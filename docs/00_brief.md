## 1. 한 문장 정의

> `초안` — 확정된 결정에서 도출했습니다. 문장이 어색하면 여기부터 고쳐주세요. 아래 모든 절이 이 문장에 매달려 있습니다.

> **Replai는 IT 직군(PM·PD·보안·AI·개발자) 경력 이직자가 수시 채용 면접을 준비할 때,
> 자기 이력서를 파고드는 꼬리질문을 받아볼 상대가 없다는 문제를 겪을 때,
> 이력서와 JD를 읽고 되묻는 AI 면접관과의 음성 모의면접, 그리고 답변 원문을 인용한 평가 리포트를 제공해,
> 실제 면접 전에 자기 답변의 약한 고리를 스스로 발견하게 하는 서비스다.**

핵심 단어는 **꼬리질문**입니다. 질문을 던지는 것이 아니라 답변을 듣고 되묻는 것이 이 제품의 전부입니다.

## 2. 왜 만드는가

> `초안` — 실제 사용자 인터뷰로 검증되지 않은 가설입니다. 틀렸다고 판단되면 고쳐주세요.

경력 이직자가 지금 쓰는 대안과 각각의 한계:

| 대안 | 한계 |
|---|---|
| 예상 질문 리스트 암기 | **되묻지 않습니다.** 준비한 답을 말하는 연습일 뿐, 그 답이 깨지는 경험을 못 합니다 |
| 면접 스터디 | 모집·일정 조율 비용이 큽니다. 경력자는 직무가 제각각이라 상대가 내 도메인을 몰라 깊이 있는 꼬리질문이 안 나옵니다 |
| 지인·현직자 모의면접 | 관계 비용 때문에 반복이 어렵고, 상대가 봐줍니다. 압박 면접이 안 됩니다 |
| 유료 코칭 | 비용과 예약. 반복 연습 수단이 못 됩니다 |
| 혼자 녹음해서 들어보기 | 상호작용이 없고, 자기 답변의 논리적 허점은 스스로 잘 안 보입니다 |

**한 가지만 고른다면:** 되묻는다는 것.
정적 질문 리스트는 "왜 그렇게 하셨죠?"를 하지 않습니다. 경력 면접에서 당락을 가르는 건 첫 답변이 아니라 세 번째 꼬리질문이고, 그걸 연습할 수단이 지금 없습니다.

**부차적 이점:** 반복 가능(관계 비용 0), 24시간 가용, 매번 같은 기준으로 채점되어 회차 간 비교가 됩니다.

## 3. 타깃 사용자

| 항목 | 내용 |
|---|---|
| 1차 타깃 (primary) | IT 산업 **경력 이직자** — PM, PD, 보안, AI, 개발자 |
| 2차 타깃 (secondary) | 같은 직군의 **신입** |
| 준비 중인 것 | **수시 채용 (경력 이직) 전용 (확정).** 공채는 신입 타깃·경험 탐색형 페르소나와 함께 후속 |
| 면접 유형 | 직무 면접 (4절 참조) |
| 사용 시점 | **지원 포지션의 서류 합격 이후, 면접 D-7 집중 연습 (확정)** |
| 명시적 제외 대상 | 한국어 외 언어 면접 준비자 — 서비스가 한국어 전용 |

**이 선택의 함의**
- 경력자가 primary이므로 **이력서·JD 컨텍스트가 필수 입력**입니다. 질문이 사용자의 실제 경험을 파고들지 못하면 경력자에게는 가치가 없습니다. (6절에서 JD·이력서 파싱을 Non-goal에서 제외한 이유)
- 사용 시점이 **서류 합격 이후 D-7**이므로 사용자는 **특정 공고의 JD를 손에 쥔 상태**로 들어옵니다. JD 입력은 선택 기능이 아니라 세션 시작의 전제이고, 재시도율(5절 #3)의 7일 창이 이 사용 패턴과 정확히 겹칩니다.
  - 뒤집어 말하면 **유입은 산발적**입니다. 상시 접속하는 제품이 아니므로 D-7이라는 한 번의 기간 안에서 몇 회를 반복하는지가 곧 제품 가치입니다. 상시 리텐션을 올리려는 기능(데일리 연습, 스트릭 등)은 이 정의와 어긋납니다.
- 직군이 5개(PM/PD/보안/AI/개발자)로 넓습니다. **분화 방식 확정: 공통 루브릭 + 직군별 질문 풀.** 평가 축과 척도는 5개 직군 공통이고, 직군별로 달라지는 것은 질문 생성뿐입니다. 스키마가 단순해지고 직군 간 리포트 비교가 가능해집니다.
- **반복 사용은 사실상 본인 API 키를 전제로 합니다.** 우리 비용으로 제공하는 체험은 서비스 전체에 하루 정원이 있고 넉넉하지 않습니다(7절 예산). 그래서 D-7 기간에 여러 번 반복하려는 사용자는 본인 Google 계정으로 API 키를 발급해 연결하게 됩니다.
  - 제외 대상으로 두지는 않지만, **Google 계정을 만들 수 없거나 키 발급을 원하지 않는 사용자는 체험 이후 사실상 이용이 어렵습니다.** 이 이탈의 크기를 모르므로 9절 #10에서 잽니다.

## 4. 면접관 페르소나 — 제품의 핵심 차별점

면접 유형은 **직무 면접** 하나지만, 면접관 **페르소나를 3종**으로 나눕니다.
사용자가 세션 시작 시 선택합니다. 이것이 이 서비스의 주된 차별점입니다.

| 페르소나 | 주 대상 | 질문 방식 | 평가 축의 무게중심 | MVP |
|---|---|---|---|---|
| **심층 압박형** | 경력 (primary) | 논리적 검증, 날카로운 꼬리질문. 주장의 근거를 계속 파고듦 | 논리 일관성, 근거의 견고함 | **포함** |
| **기술 검증형** | 경력 (primary) | 설계·CS·성능. why/how 집중 검증 | 직무 지식의 정확성과 깊이 | **포함** |
| **경험 탐색형** | 신입 (secondary) | 경험을 넓게 훑고 맥락을 끌어냄. 압박 없음 | 구조화(STAR), 구체성 | 후속 |

**설계 시 유의**
- 페르소나는 **프롬프트 차이만이 아닙니다.** 꼬리질문 생성 전략, 세션당 질문 수, 평가 루브릭 가중치가 함께 달라집니다.
- **MVP 범위: 경력용 2종(심층 압박형 + 기술 검증형) (확정).** 경험 탐색형은 신입 타깃과 함께 후속으로 미룹니다.
- 심층 압박형은 **압박의 상한**이 필요합니다. 사용자를 무너뜨리는 것이 목적이 아니라 논리를 검증하는 것이 목적입니다. → 9절 열린 질문 #2

## 4-1. 핵심 사용자 가치

> `초안` — 1·2절에서 도출. 우선순위 순.

1. **내 이력서를 읽은 면접관에게 꼬리질문을 받는다.**
   일반적인 질문이 아니라 내가 쓴 프로젝트를 지목해 되묻습니다. 이게 없으면 예상 질문 리스트와 다를 게 없습니다.
2. **점수마다 내 말이 인용된 리포트를 받는다.**
   "구조화 3점"이 아니라 "3점 — '그래서 성능이 좋아졌습니다'라고 하셨는데 수치가 없었습니다". 근거 없는 점수는 사용자가 받아들이지 않습니다.
3. **약한 고리를 알고 다시 한다.**
   같은 이력서로 다시 봤을 때 지난번 무너진 지점이 어떻게 달라졌는지 보입니다. 1회성이면 이 제품은 필요 없습니다.

판단 기준: 이 중 하나라도 빠지면 사용자가 다시 안 온다고 말할 수 있어야 합니다.
→ 3번이 재시도율(5절)로, 2번이 리포트 유용성으로 측정됩니다.

## 5. 성공 지표

> **목표 수치를 두지 않는 것이 확정된 결정입니다.** 미결이 아니라 의도된 공백입니다.
> MVP 기간은 **베이스라인 수집 기간**으로 둡니다 — 무엇을 셀지만 정의하고, 첫 사용자 20~30명의
> 실제 분포를 본 뒤에 목표치를 정합니다. 근거 없는 목표치는 판단을 돕는 대신 왜곡합니다.

| # | 지표 | 정의 | 왜 보나 | 목표 |
|---|---|---|---|---|
| 1 | **세션 완주율** | `in_progress`에 진입한 세션 중 `completed`에 도달한 비율 | 압박형 면접이 사용자를 도중에 나가게 만드는지. 압박 상한(열린 질문 #2)의 판단 근거 | 베이스라인 수집 |
| 2 | **리포트 도달률** | `completed` 세션 중 리포트 화면을 실제로 연 비율 | 평가가 비동기라 완주해도 리포트를 안 볼 수 있습니다. 여기가 새면 알림/대기 UX 문제 | 베이스라인 수집 |
| 3 | **재시도율** ⭐ | 리포트를 본 뒤 7일 내 새 세션을 시작한 비율 | **북극성 지표.** 핵심 가치 3번이 작동하는지를 직접 잰다 | 베이스라인 수집 |
| 4 | **리포트 유용성** | 리포트 하단 "이 피드백이 도움이 되었나요" 응답 중 긍정 비율 | 근거 인용이 실제로 설득력이 있는지 | 베이스라인 수집 |
| 5 | **평가 이의 제기율** | 리포트 항목별 "이건 아닌 것 같아요" 클릭 비율 | 4번의 반대 신호. 전사 오류·평가 오류를 잡는 조기 경보 (열린 질문 #3과 연결) | 낮을수록 좋음 |
| 6 | **꼬리질문 깊이** | 세션당 최초 질문 대비 후속 질문 수의 중앙값 | 제품의 정체성이 작동하는지. 이게 1에 가까우면 질문 리스트와 다를 게 없습니다 | 베이스라인 수집 |

**측정 전제**
- 4번과 5번은 리포트 화면에 수집 UI가 있어야 합니다. → 스펙의 화면 목록에 반영 필요
- 6번은 대화 로그에 "이 질문이 어느 질문의 꼬리인지"를 기록해야 셉니다. → 도메인 모델에 반영 필요

이 두 줄은 product-architect가 스펙을 쓸 때 반드시 반영해야 하는 요구사항입니다.

## 6. 하지 않을 것 (Non-goals)

범위를 지키는 문서입니다. 여기 적힌 것은 "나중에"가 아니라 **"이번엔 안 함"**입니다.

- **화상/표정 분석** — 카메라 기반 시선·표정·자세 분석 없음. 음성과 텍스트만.
- **공유·랭킹·커뮤니티** — 결과 공유, 사용자 간 비교 없음. 모든 데이터는 본인만 접근.
- **결제·구독** — 우리가 요금을 받지 않습니다. 유료 플랜도, 사용자 등급도 없습니다.
  - 다만 **무제한이 곧 무한은 아닙니다.** 우리 비용으로 제공하는 체험에는 서비스 전체의 하루 상한이 있고, 그 상한은 사용자를 등급으로 나누지 않습니다. 전원이 같은 여력을 나눠 씁니다.
  - 사용자가 **본인 API 키를 연결하면 이 상한과 무관**해집니다. 이것은 유료 플랜이 아니라 자기 자원을 쓰는 것이며, 우리가 받는 돈은 여전히 0원입니다. (7절 BYOK)
- **영어 등 한국어 외 언어 면접** — 서비스는 한국어 전용 (확정, CLAUDE.md)
- **음성 원본 보관** — 전사 텍스트만 남기고 오디오는 폐기 (7절 참조)
- **외부 전송 자체를 없애는 것** — 면접을 AI가 진행하는 이상 이력서와 답변은 AI 프로바이더로 전송됩니다. 우리가 통제하는 것은 **무엇을 보관하느냐**이지 **보내지 않는 것**이 아닙니다. 어디로 어떻게 나가는지는 7절 개인정보 항목에 적습니다.

**MVP에 포함되는 것** (Non-goal이 아님을 명시)
- **이력서·JD 입력과 활용** — 경력자가 primary이므로 필수. **입력 방식은 두 가지를 모두 지원 (확정):** 파일 업로드(PDF 등)와 텍스트 직접 입력.
  - 부수 효과: 파일 업로드 때문에 **Supabase Storage 버킷과 RLS 정책이 MVP에 필요**해집니다. 음성을 저장하지 않아 Storage가 불필요할 뻔했으나, 이력서 파일이 그 자리를 대신합니다. 이력서는 음성만큼 민감하므로 보존 기간과 삭제 정책이 필요합니다. → 9절 열린 질문 #5
- **본인 API 키 연결(BYOK)과 체험 1회** — 7절 참조.

## 7. 확정된 제약

변경하려면 CLAUDE.md와 `.claude/HARNESS_CHANGELOG.md`를 함께 고쳐야 합니다.

**기술**
- Next.js + React, UI는 **shadcn/ui 단독**. 다른 UI 라이브러리 금지.
- 데이터는 Supabase. 사용자 데이터를 담는 모든 테이블은 **예외 없이 RLS 활성화**.
- 배포는 Vercel.
- 네이밍: DB는 snake_case, API 응답과 프론트 타입은 camelCase. 변환은 **API 라우트에서 단 한 번**.
- AI 프로바이더 키와 Supabase service_role 키에 `NEXT_PUBLIC_` 접두사 금지.

**제품**
- 음성이 주 모달리티, 텍스트 채팅은 동등한 1급 시민. 대화 로그의 진실의 원천은 **텍스트 전사**.
- 서비스 언어는 한국어. AI 면접관은 한국어로 면접을 진행.

**미확정 제약**
- 예산: **각 프로바이더의 무료 티어 한도 안에서 해결 (확정).** 의미는 **"운영자가 서비스를 만들고 운영하면서 비용을 지불하지 않는다"** 이지, 사용자를 요금제로 나눈다는 뜻이 아닙니다. 사용자에게 "무료 티어"·"한도"·"쿼터" 같은 내부 용어를 노출하지 않습니다.
  - 함의 1: **Realtime 계열 음성 API는 후보에서 제외됩니다.** 무료 티어가 없거나 실질적으로 쓸 수 없습니다. 지연시간 5초 목표가 직렬 STT→LLM→TTS로 충족되므로 손실은 없습니다.
  - 함의 2: STT/TTS는 **브라우저 내장 API**를 씁니다. LLM은 무료 티어가 있는 모델이어야 하므로 **Claude는 후보가 아닙니다**(전 모델 종량 과금). Google Gemini를 씁니다. 인프라(Supabase·Vercel)도 무료 플랜 한도를 전제로 설계합니다.
  - 함의 3: **무료 키로 쓸 수 있는 것은 경량 모델뿐입니다 (2026-09-11 실측).** 상위(Pro) 모델은 무료 티어 여력이 0이라 쓸 수 없습니다. 평가 품질이 제품 신뢰의 전부인데(4-1절 핵심 가치 2번) 가장 좋은 채점 수단이 없다는 뜻입니다. 평가를 근거 추출과 채점의 두 단계로 나눠 **인용 환각은 구조적으로 막지만, 판단의 깊이는 되돌려주지 못합니다.** 점수가 중앙으로 몰릴 위험이 실재합니다. → 9절 열린 질문 #11
  - 함의 4: 무료 티어는 **분당·일당 요청 수 제한**이 걸립니다. **면접이 도중에 끊기지 않도록 세션을 시작하기 전에 여력을 확인하고 예약합니다.** 여력이 없으면 세션을 만들지 않고, 사용자에게는 "본인 API 키를 연결하면 지금 바로 시작할 수 있다"는 출구를 줍니다.
  - 함의 5: **우리 비용으로 제공하는 체험은 서비스 전체에서 하루 12건입니다 (2026-09-11 실측 기준).** 사용자당이 아니라 전 사용자를 합쳐서입니다. 13번째 사용자는 시작 전에 막힙니다. 이것이 $0 제약의 실제 가격이며, 그 귀결로 **본인 API 키 연결이 사실상 기본 경로이고 체험은 맛보기**입니다.
  - 함의 6: 무료 티어 STT의 정확도는 상용 대비 낮습니다. 음성 미저장 전제와 겹쳐 전사 오류의 위험이 커집니다. → 9절 열린 질문 #3
- BYOK(Bring Your Own Key): **사용자가 본인 Gemini API 키를 연결해 자기 토큰으로 면접을 봅니다 (확정).** 첫 세션은 체험으로 우리 키를 쓰고, 이후는 본인 키입니다. 키 연결을 요구하는 시점은 **첫 리포트를 본 직후**입니다 — 가치를 먼저 보여주고, "다시 해봐야겠다"고 느끼는 순간에 요구합니다.
  - **한도 회피 수단이 아니라 프라이버시 업그레이드 경로입니다.** 결제를 활성화한 본인 키는 유료 티어 데이터 보호를 받고, 비용은 사용자가 부담하며 우리는 0원을 유지합니다. 무료 키를 연결하더라도 본인 계정에서 본인 데이터에 대해 본인이 동의한 구조가 됩니다.
  - 채점은 재원과 무관하게 **전원 같은 파이프라인**을 씁니다. 본인 키가 더 좋은 모델을 쓸 수 있더라도 채점 모델을 바꾸지 않습니다 — 같은 전사에 재원에 따라 다른 점수가 나오면 회차 간 비교와 이의 제기 대응이 무너집니다.
  - 부수 효과: **타인의 자격증명을 보관하게 됩니다.** 저장 시 암호화가 필수이고, 한 번 저장한 키는 화면에 다시 표시하지 않으며(끝 4자리만), 계정 삭제 시 함께 파기됩니다.
- 지연시간: **답변 종료 → 다음 질문 발화까지 최대 5초 (확정).** STT→LLM→TTS 직렬 구성으로 충분하며, Realtime 계열 API가 강제되지 않습니다.
  - 전제 조건: 5초의 침묵은 사용자에게 오류로 보입니다. **"면접관이 생각 중" 상태를 UI와 오디오로 명확히 표현**하는 것이 필수 요구사항입니다. → 9절 열린 질문 #6
- 일정: **MVP 목표 시점 2026-12-02 (착수 2026-09-09 기준 12주) (확정).** 8절 '포함' 범위 전체에 더해 9절 열린 질문 해소와 QA·튜닝까지 포함한 일정입니다.
- 개인정보 ①: **음성 원본은 저장하지 않음 (확정).** 전사 텍스트만 DB에 남기고 오디오 버퍼는 세션 종료 시 폐기합니다. 대화 로그의 진실의 원천이 텍스트라는 원칙과 일치하며, 오디오 보존 정책이 불필요해집니다. 브라우저 내장 음성 인식을 쓰므로 오디오 바이트가 애초에 우리 서버에 도달하지 않습니다.
  - 부수 효과: 전사 품질이 **평가 근거 인용의 유일한 원천**이 됩니다. 전사가 틀리면 되돌아가 확인할 방법이 없으므로, STT 정확도 요구 수준이 올라갑니다. → 9절 열린 질문 #3
- 개인정보 ②: **이력서와 답변은 AI 프로바이더로 전송되며, 무료 티어에서는 사람이 읽을 수 있습니다 (확정, 2026-09-10 약관 확인).** 이것이 이 제품의 가장 큰 개인정보 노출입니다.
  - Google Gemini API 무료 서비스 약관은 제출한 콘텐츠를 **제품 개선에 사용**할 수 있고, **검토자가 읽고 주석을 달 수 있으며**, **민감·기밀·개인 정보를 보내지 말라**고 명시합니다. 유료 티어는 제품 개선에 쓰지 않습니다. 한국은 EU·영국·스위스와 달리 무료 티어에 유료 수준 보호가 적용되지 않습니다.
  - 대응은 **감추지 않는 것**입니다. 체험 면접 전에 무슨 일이 일어나는지 평범한 한국어로 알리고 **명시적 동의**를 받습니다. 동의를 거부하면 체험을 시작하지 않고 본인 API 키 연결로 안내합니다.
  - 근본 해법은 위 BYOK 항목입니다.
- 답변 텍스트 보존 기간: **무기한 보관, 사용자가 삭제할 때만 삭제 (확정).** 자동 만료 없음. 전사 텍스트·리포트·이력서 파일 모두 같은 정책이며, 삭제는 플래그를 세우는 소프트 삭제가 아니라 DB 행과 Storage 객체의 실제 제거입니다.
  - 부수 효과 1: 만료가 없으므로 **사용자의 삭제 요청이 유일한 삭제 경로**입니다. 세션 단위 삭제와 계정 삭제 UI가 MVP 필수 화면이 됩니다. → 스펙의 화면 목록에 반영 필요
  - 부수 효과 2: 이력서 파일이 무기한 남아 **Storage 무료 티어 용량이 누적 압박**을 받습니다. 위 예산 제약과 함께 봐야 합니다.
  - 부수 효과 3: 회차 간 비교(4-1절 핵심 가치 3번)에 기간 제한이 사라집니다. 이 결정으로 얻는 것입니다.

## 8. 첫 버전의 범위

> `초안` — 확정된 결정을 한 줄로 합친 것입니다.

**MVP 한 줄 정의**

> IT 직군 경력자가 이력서와 JD를 넣고, **심층 압박형 / 기술 검증형** 중 하나를 골라
> **음성으로 모의면접**을 치른 뒤, **답변 원문이 인용된 평가 리포트**를 받는다.

**포함**

| 영역 | 내용 |
|---|---|
| 인증 | 로그인/회원가입. 모든 데이터는 본인만 접근 (RLS) |
| 세션 설정 | 직군 선택(5종), 페르소나 선택(2종), 이력서·JD 입력(파일 업로드 + 텍스트 직접 입력) |
| 이용 방식 | 체험 1회(데이터 처리 동의 후), 이후 본인 API 키 연결·교체·해제 |
| 면접 | 음성 대화, 꼬리질문, 텍스트 폴백(마이크 실패 시 세션 유지한 채 전환) |
| 평가 | 공통 루브릭 채점 + 축별 답변 원문 인용 |
| 리포트 | 점수·근거·개선점, 유용성 피드백·항목별 이의 제기 수집 UI |
| 이력 | 지난 세션 목록과 리포트 다시 보기, 세션 삭제·계정 삭제 |

**제외** (6절 Non-goals + 후속)
화상/표정 분석, 공유·랭킹·커뮤니티, 결제·구독, 한국어 외 언어, 음성 원본 보관, 경험 탐색형 페르소나(신입 타깃과 함께 후속)

**"이것만 되면 보여줄 수 있다"의 최소선**
위 표에서 더 줄인다면 마지막까지 남는 것은 이 셋입니다 — **이력서를 읽은 꼬리질문 / 원문 인용 평가 / 음성 대화.**
셋 중 하나라도 빠지면 데모의 의미가 없습니다.
