## 1. 설계 원칙

1. **텍스트가 정본이다.** 음성은 입력 채널이자 출력 채널일 뿐입니다. 저장되고 평가되는 것은
   `turns.transcript_text` 하나뿐이고, 음성 경로는 그 문자열을 만들어 내는 여러 방법 중 하나입니다.
   그래서 음성이 죽어도 대화는 계속됩니다.
2. **오디오는 어디에도 남지 않는다.** 저장하지 않는 것이 아니라 **애초에 축적하지 않습니다**(6절).
   버킷도 컬럼도 없고(`04_data_layer.md` 7.1), 클라이언트에도 오디오 Blob을 만드는 코드 경로가 없습니다.
3. **음성은 실패한다고 전제한다.** 권한 거부, 마이크 없음, 브라우저 미지원, 네트워크 단절, 인식 실패는
   예외가 아니라 정상 경로입니다. 모든 실패의 종착지는 **동일한 세션 안의 텍스트 모드**이고,
   세션을 죽이는 실패는 하나도 없습니다(5절 폴백 매트릭스).
4. **자동 감지는 보조, 버튼이 본체다.** 침묵 기반 턴 감지는 편의 기능이고, "답변 완료" 버튼이
   언제나 노출되는 정식 수단입니다. 면접에서 생각하느라 멈추는 침묵은 길고, 자동 감지가 그걸
   말 끊김으로 오인하면 제품 가치(꼬리질문의 근거가 되는 답변)가 손상됩니다.
5. **예산 안에서 끝난다.** 세션당 유료 과금 $0. STT/TTS는 브라우저 내장 API만 쓰므로 **우리 계정의
   무료 티어 쿼터를 전혀 소모하지 않습니다**(3.4절). 유료 과금이 발생하는 구성은 후보에서 제외했습니다.
6. **키는 클라이언트에 없다.** 브라우저 내장 API만 쓰므로 STT/TTS용 토큰 발급 라우트 자체가
   필요 없습니다. 이것이 이 선택의 부수적이지만 중요한 이점입니다(3.5절).

## 2. 파이프라인 전체 구조

### 2.1 흐름도

```
                        ┌──────────────────── 브라우저 ────────────────────┐
                        │                                                  │
[사용자 발화] ──음향──▶ │ ❶ getUserMedia (분석 전용 스트림)                │
                        │      └─▶ AudioContext → AnalyserNode             │
                        │             ├─▶ RMS 레벨 (VU 미터 · UI)          │
                        │             └─▶ ❷ 턴 감지 (침묵 타이머 + 버튼)   │
                        │                                                  │
                        │ ❸ SpeechRecognition (Web Speech API)             │
                        │      ├─ interim 결과 ──▶ 화면 실시간 표시        │
                        │      └─ final 결과   ──▶ 발화 텍스트 확정        │
                        │                          + confidence            │
                        └────────────────────┬─────────────────────────────┘
                                             │ POST /api/sessions/[id]/turns
                                             │ { transcriptText, transcriptRaw,
                                             │   modality:'voice', sttConfidence }
                                             ▼
                        ┌──────────────── 서버(Vercel) ────────────────────┐
                        │ ❹ turns 삽입 (transcript_text = 정본)            │
                        │ ❺ Interviewer LLM 호출 (SSE 스트림)              │
                        │      └─ 문장 청크 분할 + <<<META>>> 차단(7절)    │
                        └────────────────────┬─────────────────────────────┘
                                             │ SSE: utterance_chunk / utterance_done
                                             │      session_notice / stream_error
                        ┌────────────────────▼─────────────────────────────┐
                        │ ❻ 청크 수신 → 화면 즉시 렌더 (텍스트가 먼저다)   │
                        │ ❼ speechSynthesis.speak(청크) — 큐에 순차 적재   │
                        │ ❽ barge-in 감시 (재생 중 사용자 발화 / 버튼)     │
                        └──────────────────────────────────────────────────┘
```

### 2.2 단계별 책임과 경계

| # | 단계 | 책임 | 이 단계가 하지 않는 것 | 실패 시 (5절 참조) |
|---|---|---|---|---|
| ❶ | 마이크 캡처 | 권한 획득, 장치 선택, 에코 취소·노이즈 억제 옵션 지정, 오디오 그래프 구성 | **녹음하지 않는다.** `MediaRecorder`를 쓰지 않고 Blob/ArrayBuffer를 만들지 않는다 | `mic_permission_denied` / `mic_unavailable` |
| ❷ | 턴 감지(VAD) | 발화 시작·종료 판정, 침묵 카운트다운 표시, "답변 완료" 버튼 처리 | 전사하지 않는다. 텍스트를 보지 않고 **소리와 시간만** 본다(단, 적응 임계값은 ❸의 interim 텍스트를 참조 — 4.3절) | 자동 감지 비활성화, 버튼 전용 모드 |
| ❸ | STT | `SpeechRecognition`으로 interim/final 전사 생성, `confidence` 수집, 언어 `ko-KR` 명시 | 턴을 확정하지 않는다. 브라우저의 자체 엔드포인팅은 **참고만** 하고 턴 확정 권한은 ❷에 있다 | `stt_unsupported` / `stt_error` / `stt_empty` |
| ❹ | 발화 커밋 | 정규화(공백·중복 정리) 후 서버로 1회 전송. 낙관적 UI 렌더 | 오디오를 함께 보내지 않는다 | 재시도 3회 → `paused(connection_lost)` |
| ❺ | 면접관 생성 | (서버 책임) LLM 스트림, 청크 분할, 센티널 차단 | — | `stream_error` → 폴백 사다리 |
| ❻ | 청크 수신·렌더 | SSE 파싱, 화면에 텍스트 즉시 추가 | — | 텍스트만 남고 계속 진행 |
| ❼ | TTS 재생 | 청크를 `SpeechSynthesisUtterance`로 큐에 적재, 순차 재생, 문장 단위 파이프라이닝 | 텍스트 렌더를 막지 않는다. **TTS가 실패해도 화면 텍스트는 이미 떠 있다** | `tts_unavailable` → 무음 진행 |
| ❽ | barge-in | 재생 중단, 잔여 큐 폐기, 그 시점까지의 발화를 서버에 알림 | 서버의 `turns` 저장을 결정하지 않는다(서버가 M7 규칙으로 확정) | — |

**경계에서 자주 새는 지점 (명시적 금지)**

| 금지 | 이유 |
|---|---|
| ❸이 턴을 확정하는 것 | Chrome의 기본 엔드포인팅은 1~2초 수준이라 면접의 생각 침묵을 말 끊김으로 오인한다. 턴 확정은 반드시 ❷ |
| ❼이 완료되어야 ❻을 렌더하는 것 | 텍스트는 1급 시민이자 정본이다. 오디오는 텍스트를 기다리게 만들 수 없다 |
| ❶이 `MediaRecorder`를 쓰는 것 | 오디오 버퍼가 생기는 즉시 "미저장 보장"이 코드 리뷰 신뢰의 문제로 격하된다(6절) |
| 클라이언트가 `<<<META>>>`를 파싱하는 것 | 센티널 차단은 서버 책임이며 클라이언트는 센티널을 **볼 일이 없어야** 한다. 클라이언트에 방어 코드를 두면 서버 누수가 은폐된다(7.3절) |

## 3. STT / TTS 기술 선택과 근거

### 3.1 후보와 탈락 사유

| 후보 | 세션당 비용 | 판정 | 근거 |
|---|---|---|---|
| Realtime 계열 음성 API (양방향 스트리밍) | 유료 | **탈락 (제약)** | 브리프 7절에서 명시적으로 제외. 무료 티어가 없거나 실질적으로 쓸 수 없음 |
| 상용 스트리밍 STT (관리형 SaaS) | 유료 또는 크레딧 소진형 | **탈락 (예산)** | 무료 크레딧은 일회성이라 "세션당 $0"을 지속적으로 만족하지 못함 |
| 서버에서 오디오 업로드 → 배치 STT | 유료 + 지연 | **탈락 (예산·지연·원칙)** | 비용 문제에 더해, 오디오를 서버로 올리는 순간 **"오디오 버퍼를 만들지 않는다"는 6절 구조가 무너진다** |
| 브라우저 내장 `SpeechRecognition` (Web Speech API) | **$0** | **채택 (STT)** | 3.2절 |
| 브라우저 내장 `speechSynthesis` (Web Speech API) | **$0** | **채택 (TTS)** | 3.3절 |

### 3.2 STT: `SpeechRecognition` (Web Speech API)

**설정 (구현 규약)**

| 속성 | 값 | 이유 |
|---|---|---|
| `lang` | `'ko-KR'` **명시 고정** | 자동 감지는 한국어에 영어 기술용어가 섞이는 발화("이 API의 레이턴시가...")에서 오판한다. 면접 발화는 코드 스위칭이 상수다 |
| `continuous` | `true` | 한 답변이 여러 문장이다. `false`면 첫 문장에서 끊긴다 |
| `interimResults` | `true` | 화면 실시간 표시와 적응 임계값(4.3절)의 입력. 무엇보다 **엔드포인트 시점에 최종 전사가 이미 거의 완성돼 있어 지연 예산을 지키는 핵심**(8절) |
| `maxAlternatives` | `1` | 대안을 쓰지 않는다. 정정은 사용자가 한다(9절) |

**정직하게 적는 한계**

| # | 한계 | 영향 | 대응 |
|---|---|---|---|
| L1 | **브라우저 지원 편차가 크다.** Chrome/Edge 계열과 Safari는 지원하지만 Firefox는 기본 설정에서 `SpeechRecognition`을 제공하지 않는다 | Firefox 사용자는 **음성 모드 자체가 불가** | 3.6절 기능 탐지 → `ready` 화면에서 차단하고 텍스트 모드로 안내. 세션은 정상 진행 |
| L2 | **Chrome 계열의 클라우드 인식은 오디오를 브라우저 벤더 서버로 전송한다.** 우리가 저장하지 않는 것과 별개로 **제3자 전송은 일어난다** | 브리프 7절의 개인정보 약속을 사용자가 오해할 수 있음 | 6.4절 동의 문구에 **반드시 명시**. 온디바이스 인식이 가능한 환경에서는 그쪽을 우선(L7) |
| L3 | **한국어 정확도가 상용 대비 낮다.** 특히 영어 기술용어, 고유명사(제품·프레임워크명), 숫자+단위("p99 이백 밀리초") | 전사가 평가 인용의 유일한 원천이므로 오류가 리포트에 그대로 남는다(브리프 7절 함의 4) | (a) 직전 발화 정정 기능(9절), (b) `stt_confidence` 저장, (c) `transcript_raw` 보존 |
| L4 | **연속 인식이 임의로 종료된다.** 긴 침묵이나 내부 타임아웃으로 `onend`가 발생하며, 명시적 `stop()` 없이도 끊긴다 | 사용자가 생각하는 동안 인식기가 죽어 이후 발화가 통째로 유실 | 4.4절 **자동 재시작 루프**(`onend` → 턴이 아직 열려 있으면 `start()` 재호출, 지수 백오프, 연속 실패 3회면 폴백) |
| L5 | **HTTPS(보안 컨텍스트)가 필수다.** `getUserMedia`도 동일 | 로컬 개발에서 `http://` 접속 시 음성 전 기능이 죽는다 | Vercel 배포는 항상 HTTPS. 로컬은 `localhost`가 보안 컨텍스트로 취급되므로 **`localhost`로만 개발**한다. LAN IP 접속 금지를 개발 문서에 명시 |
| L6 | **`confidence` 값이 신뢰할 수 없다.** 구현체에 따라 `0`, `1`, 또는 누락 | `stt_confidence`로 품질 관측을 하려던 계획이 흔들림 | 값이 유한하고 `0 < c <= 1`일 때만 저장하고 그 외에는 **`NULL`**. `04_data_layer.md`가 NULL 허용이므로 스키마 변경 불필요 |
| L7 | 최신 Chrome 계열은 온디바이스 음성 인식 경로(가용성 조회 + 로컬 처리 플래그)를 제공한다고 알려져 있으나, **한국어 모델 제공 여부와 API 표면을 이 문서에서 확정하지 않는다** | L2 완화 가능성 | **[확인 필요]** Phase 3 착수 시 실제 브라우저에서 가용성 조회 API의 존재와 `ko-KR` 지원을 측정하고 결과를 이 절에 기록한다. 지원되면 온디바이스를 우선 시도하고 실패 시 클라우드로 강등한다. **가정하고 설계하지 않는다** — 현재 설계는 클라우드 인식만 전제해도 성립한다 |

> L1·L2·L7의 브라우저별 실제 동작은 **측정이 필요한 항목**입니다. 3.6절의 검증 과제로 등록했습니다.

### 3.3 TTS: `speechSynthesis` (Web Speech API)

**설정 (구현 규약)**

| 항목 | 규약 | 이유 |
|---|---|---|
| 음성 선택 | `getVoices()`에서 `lang`이 `ko-KR`/`ko_KR`로 시작하는 것만 후보. 그중 **`localService === true`를 최우선** 선택 | 로컬 음성은 네트워크 왕복이 없어 첫 오디오까지가 짧다. 원격 음성은 8절 예산을 위협한다 |
| 음성 없음 | `ko` 음성이 0개면 **TTS를 켜지 않고** 텍스트 전용으로 진행 | 영어 음성으로 한국어를 읽으면 알아들을 수 없다. 무음이 낫다 |
| `rate` | `1.0` (사용자 조절 `0.8~1.2`) | 면접관 발화 속도. 기본은 손대지 않는다 |
| 세션당 고정 | 세션 시작 시 음성을 1회 선택해 고정 | 청크마다 다른 목소리가 나오면 면접관이 여러 명이 된다 |
| 입력 텍스트 | 서버가 보낸 `utterance_chunk.text` **그대로**. 클라이언트에서 가공하지 않음 | 계약 M5가 이미 TTS가 읽을 수 없는 것(JSON·마크다운·이모지·번호 목록)을 금지했다 |

**정직하게 적는 한계**

| # | 한계 | 영향 | 대응 |
|---|---|---|---|
| T1 | **설치된 한국어 음성의 유무와 품질이 OS·브라우저마다 다르다.** 데스크톱 Linux 등에서는 한국어 음성이 아예 없을 수 있다 | 면접관 목소리가 없거나 어색함 | 위 "음성 없음" 규약. `ready` 화면에서 **샘플 발화를 1회 재생해 사용자가 미리 확인**하게 한다 |
| T2 | **원격(네트워크) 음성은 첫 오디오 지연이 크고 오프라인에서 실패한다** | 8절 TTS 예산 900ms 초과 위험 | `localService` 우선. 로컬이 없어 원격을 쓸 때는 `ready` 화면에 "네트워크 상태에 따라 면접관 음성이 늦을 수 있습니다" 고지 |
| T3 | **오디오 바이트에 접근할 수 없다.** 재생만 가능하고 스트림을 가로챌 수 없다 | 오디오 저장이 **구조적으로 불가능** | 이건 한계가 아니라 **이점**이다. 6절의 미저장 보장을 코드 규율이 아니라 플랫폼이 강제한다 |
| T4 | **자동 재생 정책.** 사용자 제스처 없이 첫 발화를 재생하면 브라우저가 막을 수 있다 | 오프닝 질문이 무음으로 지나감 | `ready` → `in_progress` 전이는 **항상 사용자의 "면접 시작" 클릭**이므로(상태 머신 2절) 이 제스처 안에서 `speechSynthesis`를 한 번 워밍업(빈 발화 재생)한다 |
| T5 | **일시정지 후 재개 시 큐가 엉키는 구현체가 있다** | 발화가 중복되거나 멈춤 | 모든 중단은 `cancel()`로 큐를 **완전히 비우고** 다시 채운다. `pause()`/`resume()`은 쓰지 않는다 |
| T6 | 긴 텍스트에서 재생이 중간에 끊기는 구현체가 있다 | — | 청크 최대 80자(계약 6.2절 2항)가 이미 이 위험을 회피한다. **계약이 우리를 지켜준다** |

### 3.4 이 선택이 예산 제약에서 갖는 의미 (중요)

브라우저 내장 API는 **우리 계정의 API 키를 쓰지 않습니다.** 따라서:

- STT/TTS는 `02_ai_architecture.md` 8절의 무료 티어 호출 예산을 **전혀 소모하지 않습니다.**
  세션당 LLM 호출만 계산하면 됩니다.
- `01_state_machine.md` 4절 폴백 사다리의 1·2단계는 "**우리가 산 쿼터의 소진**"이 아니라
  "**브라우저/플랫폼이 제공하는 기능의 일시적 불가**"로 재해석해야 합니다. → 15절 불일치 #1
- 반대급부: 우리가 통제할 수 없습니다. 프로바이더 교체 레버가 없고, 품질도 협상 대상이 아닙니다.
  이것이 L3(정확도)에 대해 정정 기능(9절)이 **선택이 아니라 필수**인 이유입니다.

### 3.5 아키텍처 선택: 서버 경유 vs 브라우저 직결

**결정: 오디오는 브라우저 밖으로 나가지 않는다. 서버로는 확정된 텍스트만 간다.**

`voice-text-dual-modality` 스킬은 실시간 양방향 스트리밍이 필요할 때 브라우저↔프로바이더 직결과
단기 토큰 발급 엔드포인트를 권합니다. **이 프로젝트에는 그 엔드포인트가 필요 없습니다.**

- 대화가 **턴 기반**입니다. 발화가 끝난 뒤 처리하므로 장시간 양방향 오디오 스트림이 없습니다.
  Vercel 함수의 실행 상한과 스테이트리스 특성이 문제 되지 않습니다.
- STT/TTS가 **브라우저 내장**이라 인증할 프로바이더가 없습니다. 발급할 토큰이 없으므로
  `POST /api/voice/token` 같은 라우트를 **만들지 않습니다.**
- 서버로 가는 유일한 오디오 유래 데이터는 **UTF-8 문자열**(`transcriptText`)입니다.
- 서버 경유가 필요한 것은 LLM 스트림(SSE) 하나뿐이고, 그건 `vercel-platform-engineer`의 영역입니다.

**나중에 프로바이더를 바꾼다면** 이 결정이 뒤집힙니다. 유료 스트리밍 STT를 도입하는 순간
(a) 단기 토큰 발급 라우트, (b) 오디오 전송 경로, (c) 6절의 미저장 구조 재설계가 **한 묶음으로**
필요해집니다. 셋 중 하나만 하면 안 됩니다. 이 문단이 그때의 판단 근거입니다.

### 3.6 브라우저 기능 탐지와 검증 과제

**세션 시작 전 `ready` 화면에서 반드시 수행하는 점검** (결과는 `session_events`에 `voice_precheck` 기록):

```
1. isSecureContext                      → false면 음성 전면 불가 (L5)
2. window.SpeechRecognition
   ?? window.webkitSpeechRecognition    → 없으면 STT 불가 (L1)
3. navigator.mediaDevices.getUserMedia  → 없거나 거부되면 마이크 불가
4. speechSynthesis.getVoices()에 ko 음성 → 없으면 TTS 없이 진행 (T1)
5. 마이크 입력 레벨 3초 측정            → 무음이면 "소리가 잡히지 않습니다" 경고
6. 한국어 음성 샘플 1회 재생            → 사용자가 직접 확인 (T1/T4 워밍업 겸용)
```

1~3 중 하나라도 실패하면 `ready` 화면은 음성 모드를 **선택 불가로 만들고** 텍스트 모드로 안내합니다.
세션은 그대로 시작되고 `modality`/`current_modality`가 `'text'`로 기록됩니다.

## 4. 턴 감지 (VAD)

### 4.1 문제 정의

면접에서 침묵은 두 가지입니다.

- **생각 침묵** — "그 프로젝트에서 왜 그 선택을 했죠?"를 듣고 답을 고르는 3~4초. **끊으면 안 됩니다.**
- **종료 침묵** — 답이 끝나서 상대의 반응을 기다리는 침묵. **빨리 잡아야 5초 예산을 지킵니다.**

소리만으로는 이 둘이 구분되지 않습니다. 그래서 (a) 임계값을 넉넉히 잡고, (b) **버튼을 항상 두고**,
(c) 임계값을 텍스트 단서로 적응시킵니다.

### 4.2 신호 측정

`AudioContext` → `AnalyserNode`(`fftSize = 2048`, `smoothingTimeConstant = 0.6`)에서 20ms 주기로 RMS를 계산합니다.

- **노이즈 플로어 학습**: `ready` 화면 점검(3.6절 5번)의 3초 동안 RMS 중앙값을 측정해 `noiseFloor`로 둡니다.
- **발화 판정**: `rms > noiseFloor * 3.5` (약 +11dB)가 **연속 100ms** 이상이면 발화 중.
- **침묵 판정**: 위 조건이 깨진 시점부터 침묵 타이머 시작. 발화가 재개되면 타이머 리셋.
- 세션 중 200ms마다 `noiseFloor`를 하한 완화 방향으로만(조용해지는 방향) 재추정합니다. 시끄러워지는
  방향으로 자동 상향하면 사용자 발화 자체를 소음으로 학습해 버립니다.

**`AnalyserNode`는 분석 전용**입니다. 고정 크기 버퍼를 매 프레임 덮어쓰며 읽고 버립니다.
어디에도 누적하지 않습니다(6절).

### 4.3 임계값과 적응 규칙

```
MIN_UTTERANCE_MS            = 700    // 이보다 짧은 소리는 발화로 치지 않음 (기침·잡음)
SILENCE_THRESHOLD_MS        = 3000   // 기본 침묵 임계값
SILENCE_THRESHOLD_FINAL_MS  = 1800   // 종결 어미가 감지된 경우
COUNTDOWN_VISIBLE_MS        = 1200   // 남은 시간이 이 값 이하면 카운트다운 표시
BARGE_IN_SUSTAIN_MS         = 400    // 재생 중 이만큼 발화가 지속되면 barge-in
MAX_TURN_MS                 = 180000 // 한 답변의 하드 상한(3분). 초과 시 강제 확정
```

**기본 3000ms의 근거.** 일반 대화형 VAD의 관행값(0.5~1초)은 면접에서 쓸 수 없습니다.
생각 침묵이 3~4초라는 것이 이 제품의 전제(브리프 2절 "세 번째 꼬리질문", 스킬 지침)이고,
말을 끊긴 사용자는 답변을 다시 시작해야 하는데 그 손실이 1~2초의 지연보다 훨씬 큽니다.
"끊긴 답변"은 꼬리질문의 근거를 훼손하고 평가 인용까지 오염시킵니다. **비대칭 손실이므로 넉넉한 쪽으로 틀립니다.**

**1800ms 적응의 근거.** interim 전사의 끝이 한국어 **종결 어미**로 끝나면 문장이 완결되었을 확률이 높습니다.
이때만 임계값을 낮춰 체감 지연을 1.2초 줄입니다.

```
종결 어미 패턴(초안): (습니다|합니다|입니다|했습니다|였습니다|해요|예요|이에요|네요|
                       거든요|더라고요|같습니다|같아요|았어요|었어요|죠|지요)\s*[.?!]?$
```

이 목록은 **휴리스틱이며 튜닝 대상**입니다. 상수로 노출해 코드 수정 없이 조정할 수 있게 둡니다.
오검출(문장 중간에 "…했습니다만, " 하고 이어가려는 경우)이 발생해도 손실은 1.2초 빠른 확정뿐이고,
사용자는 다음 질문이 나오기 전이라면 barge-in으로 되돌릴 수 있습니다.

**오검출 시 동작**

| 오검출 유형 | 증상 | 동작 |
|---|---|---|
| 조기 확정 (생각 침묵을 종료로 오인) | 사용자가 아직 말할 게 있음 | 카운트다운(4.4절)이 예고했으므로 사용자가 말을 이으면 **타이머가 리셋**된다. 이미 확정됐다면 면접관 발화 중 barge-in으로 중단하고 **직전 발화 정정**(9절)으로 답변을 보완 |
| 미확정 (계속 대기) | 침묵이 3초를 넘겨도 안 넘어감 = 소음이 임계값을 계속 넘김 | 무한 대기가 되지 않도록 **"답변 완료" 버튼이 항상 노출**. 추가로 30초 이상 발화 없이 소음만 지속되면 "주변 소리가 계속 잡히고 있습니다" 안내 |
| 짧은 잡음을 발화로 오인 | 기침·클릭음으로 턴이 시작됨 | `MIN_UTTERANCE_MS = 700` 미만은 발화로 세지 않는다. 확정 시 전사가 비면 `stt_empty` 경로(5절) |
| 발화가 끝나지 않음 | 3분 초과 | `MAX_TURN_MS`에서 강제 확정 + "답변이 길어 여기까지 정리했습니다" 안내. 정정 가능 |

### 4.4 턴 확정 절차와 사용자에게 보이는 예고

**핵심: 사용자가 무슨 일이 일어날지 예측할 수 있어야 합니다.**

```
발화 감지 ──▶ [listening] + VU 미터
                │
                └─ 침묵 시작 ──▶ 남은 시간 <= 1200ms ──▶ [listening] + 원형 카운트다운
                                        │                  "곧 답변을 마칩니다"
                                        │                  ← 이 동안 말을 이으면 리셋
                                        ▼ 0
                                   턴 확정 (t=0)
                                        │
                                        ├─ 400ms 이내에 [transcribing] 표시  ← 상태 머신 6절 강제
                                        ├─ SpeechRecognition.stop() → 최종 결과 수집
                                        └─ 전사 확정 ──▶ 서버 전송 ──▶ [thinking]
```

**"답변 완료" 버튼**은 `listening` 상태에서 항상 활성입니다. 누르면 침묵 타이머를 건너뛰고 즉시 턴을 확정합니다.
이것이 정식 수단이고 침묵 감지는 보조입니다(원칙 4).

**연속 인식 자동 재시작 (L4 대응)**

```
onend 발생 시:
  턴이 아직 열려 있고 사용자가 중단하지 않았다면 → start() 재호출
  재시작 간격: 200ms → 400ms → 800ms (지수 백오프)
  연속 실패 3회 → stt_error 경로 (5절) → 텍스트 모드 전환
  재시작해도 이미 확정된 interim 텍스트는 누적 버퍼에 보존한다 (재시작이 전사를 지우지 않게)
```

## 5. barge-in (면접관 발화 중 사용자 개입)

### 5.1 감지 수단 두 가지

| 수단 | 조건 | MVP 기본값 |
|---|---|---|
| **명시적 버튼** — "말하기" / "질문 건너뛰기" | 사용자가 클릭 | **항상 활성. 이것이 기본 수단** |
| **음성 자동 감지** | `speaking` 상태에서 RMS 발화 조건이 `BARGE_IN_SUSTAIN_MS`(400ms) 지속 | **V5 실측 후 결정** — 아래 참조 |

**자동 감지를 기본값으로 두지 않는 이유.** `speechSynthesis`의 출력은 스피커로 나가고, 그 소리가 마이크로
되돌아옵니다. `getUserMedia`의 `echoCancellation: true`가 이를 상쇄하도록 되어 있지만, **`speechSynthesis`
출력이 브라우저의 오디오 처리 그래프를 거치는지가 구현체마다 다릅니다.** 상쇄되지 않으면 면접관이 말하는 동안
자기 목소리가 barge-in을 계속 발동시켜 면접이 진행되지 않습니다. 이건 세션을 죽이는 급의 고장입니다.

따라서 **V5(3.6절) 실측 전까지 자동 barge-in의 기본값은 `off`**이고, 명시적 버튼만 제공합니다.
V5에서 헤드폰 사용 시 자기 목소리 RMS가 노이즈 플로어 수준으로 떨어지는 것이 확인되면,
"헤드폰 사용 중" 옵션을 켠 사용자에 한해 자동 감지를 활성화합니다.

**`[결정 완료 D15]` 자동 barge-in은 MVP에서 기본 `off`입니다.** 명시적 "답변 시작" 버튼만 제공합니다.
에코 취소의 실효를 확인하지 못한 상태로 켜면 면접관 자신의 목소리가 사용자 발화로 인식되어
**면접 진행 자체가 불가능해질 수 있습니다.** 실패 모드가 "기능이 없다"가 아니라 "제품이 동작하지 않는다"이므로
켜고 시작하지 않습니다. V5(에코 유입량) 실측 후 재검토합니다.

### 5.2 barge-in 발생 시 동작 순서

```
1. speechSynthesis.cancel()          // 재생 즉시 중단 + 큐 전량 폐기
2. 수신 중인 SSE 스트림을 abort       // 서버에 중단이 전달됨 → 계약 M7 적용
3. 상태: speaking → listening
4. 화면: 지금까지 렌더된 면접관 텍스트는 남기고 "(중간에 답변을 시작했습니다)" 표시
5. STT 재시작 → 사용자 발화를 새 턴으로 수집
```

- **서버는 그때까지 확정된 청크까지를 `turns.transcript_text`로 저장합니다**(계약 6.2절 5항, M7).
  클라이언트는 이 저장을 결정하지 않고, 스트림 abort만 합니다. 저장 판단이 두 곳에 있으면 어긋납니다.
- META가 오지 않았으므로 서버는 M6 규칙(`action`을 `follow_up`으로 간주)을 적용합니다.
  **면접이 멈추지 않는 것이 계약입니다.**
- 화면에 이미 렌더된 텍스트를 지우지 않는 이유: 사용자가 읽은 것을 없애면 무슨 질문이었는지 확인할 방법이
  사라집니다. 오디오는 사라져도 텍스트는 남습니다 — 원칙 1의 직접적 귀결입니다.

### 5.3 barge-in이 아닌 것

| 상황 | barge-in인가 | 처리 |
|---|---|---|
| 면접관 발화 중 사용자가 기침 | 아니다 | `BARGE_IN_SUSTAIN_MS` 400ms 미만이면 무시 |
| 면접관 발화가 끝난 뒤 사용자가 말하기 시작 | 아니다 | 정상 턴 시작 (`speaking` → `listening` 전이는 재생 종료로 이미 일어남) |
| 사용자가 "일시정지" 클릭 | 아니다 | 상태 전이(`in_progress → paused`). `cancel()` 후 오디오 그래프 전체 해제(6.2절) |
| TTS는 끝났는데 텍스트 스트림은 진행 중 | 아니다 | 정상. 텍스트가 오디오보다 앞선다 |

## 6. 오디오 미저장 보장

브리프 7절 확정 제약입니다. `04_data_layer.md` 7.1절이 **오디오 버킷을 만들지 않았고**,
3.5절이 **`turns`에 오디오 경로 컬럼을 두지 않았습니다.** 이 절은 그 결정을 클라이언트 쪽에서
"실수로도 남을 수 없는" 구조로 만드는 방법을 정의합니다.

### 6.1 오디오 데이터가 존재하는 지점 전부 (총 3곳)

| # | 위치 | 형태 | 수명 | 축적 여부 |
|---|---|---|---|---|
| A1 | `MediaStream` (마이크 트랙) | OS/브라우저가 관리하는 실시간 스트림 | 트랙 `stop()`까지 | **없음.** 우리 메모리에 복사되지 않는다 |
| A2 | `AnalyserNode` 내부 버퍼 | 고정 크기(2048 float) | 매 프레임 덮어쓰기 | **없음.** `getFloatTimeDomainData`로 읽고 RMS 스칼라 하나만 남긴다 |
| A3 | `SpeechRecognition` 내부 | 브라우저 구현 내부 | 브라우저가 관리 | **접근 불가.** 우리가 만들 수도 지울 수도 없다 |

**이 목록에 없는 것이 핵심입니다.** `MediaRecorder`도, `Blob`도, `ArrayBuffer` 누적도,
`AudioBuffer` 저장도, `fetch(body: audio)`도 **없습니다.**
브라우저 밖으로 나가는 오디오 유래 데이터는 **UTF-8 문자열 하나**뿐입니다.

### 6.2 생명주기 — 언제 해제되는가

`releaseAudioGraph()` 하나로 모든 해제를 수행하고, **아래 모든 지점에서 호출**합니다.

```
releaseAudioGraph():
  1. speechRecognition.abort()                    // 인식기 중단
  2. speechSynthesis.cancel()                     // 재생 중단 + 큐 폐기
  3. analyserNode.disconnect()                    // 그래프 분리
  4. mediaStream.getTracks().forEach(t => t.stop())  // 마이크 트랙 종료 (탭 표시등 소등)
  5. audioContext.close()                         // 컨텍스트 해제
  6. 모든 참조를 null로 (mediaStream / analyser / recognition / audioContext)
```

| 호출 지점 | 근거 |
|---|---|
| `in_progress → completed` | 상태 머신 2절 "오디오 버퍼 폐기" |
| `in_progress → paused` (사유 3종 전부) | 상태 머신 2절, 5절 |
| `in_progress → failed` | 상태 머신 2절 |
| `in_progress → canceled` | 세션 실제 삭제 |
| `current_modality`가 `'voice' → 'text'`로 전환 | 텍스트 모드에서 마이크를 잡고 있을 이유가 없다 |
| React 컴포넌트 언마운트 (`useEffect` cleanup) | 라우팅 이탈 |
| `visibilitychange` → `hidden` 60초 지속 | 탭 백그라운드. 마이크를 붙잡고 있지 않는다 |
| `beforeunload` / `pagehide` | 탭 종료·새로고침 |

**마이크 트랙 종료(4번)가 사용자에게 보이는 보장입니다.** 브라우저 탭의 마이크 표시등이 꺼지는 것으로
사용자가 직접 확인할 수 있습니다. 문서상의 약속이 아니라 관찰 가능한 신호입니다.

### 6.3 실수로 남지 않게 하는 구조적 장치

문서에 "저장하지 마세요"라고 쓰는 것으로는 부족합니다. 코드 리뷰에서 놓칠 수 있는 것을
**도구가 막게** 합니다.

| # | 장치 | 내용 |
|---|---|---|
| S1 | **린트 규칙** | `no-restricted-globals`에 `MediaRecorder`, `AudioWorkletNode`, `ScriptProcessorNode`, `OfflineAudioContext` 등록. 위반 시 CI 실패. 우회하려면 규칙 파일을 고쳐야 하고, 그건 리뷰어 눈에 띈다 |
| S2 | **경로 격리** | 오디오 API 호출은 `src/lib/voice/audioGraph.ts` **한 파일**에만 존재. 다른 파일에서 `getUserMedia`/`AudioContext`를 직접 부르는 것을 린트로 금지(`no-restricted-imports` 계열 + 커스텀 규칙) |
| S3 | **타입 경계** | 이 계층이 외부로 노출하는 타입에 `Blob`·`ArrayBuffer`·`AudioBuffer`가 **등장하지 않는다**. 노출 타입은 `{ transcriptText: string; transcriptRaw: string \| null; sttConfidence: number \| null; rmsLevel: number }`. 타입 시그니처만 봐도 오디오가 못 빠져나간다 |
| S4 | **네트워크 계약** | `/api/sessions/[id]/turns` 요청 본문 스키마에 바이너리 필드가 없다. 서버가 `multipart/form-data`를 거부한다 |
| S5 | **스키마 부재** | `04_data_layer.md`에 오디오 버킷도 컬럼도 없다. 저장하려면 **마이그레이션을 새로 써야** 하고, 그 PR은 브리프 위반으로 반려된다 |
| S6 | **QA 회귀 검사** | `qa-inspector`에 검사 항목 등록: (a) 코드베이스 전역에 `MediaRecorder` 문자열이 없을 것, (b) Storage 버킷 목록에 `documents` 하나뿐일 것 |

**S5가 가장 강한 장치입니다.** 저장하려면 여러 사람이 관여하는 명시적 변경이 필요하고,
실수 한 줄로는 도달할 수 없습니다.

### 6.4 사용자 고지 (필수)

`ready` 화면과 `/sessions/new`의 모달리티 선택 지점에 **한국어로** 다음을 고지합니다.
문구는 `shadcn-ui-engineer`가 다듬되 내용은 아래를 벗어나지 않습니다.

- 음성은 **저장되지 않으며**, 대화 기록으로 남는 것은 **전사된 텍스트뿐**이라는 것
- 마이크는 면접이 끝나거나 일시정지하면 **즉시 해제**된다는 것
- **음성 인식은 브라우저가 제공하는 기능이며, 브라우저에 따라 인식을 위해 음성이 브라우저 제조사의
  서버로 전송될 수 있다는 것** (L2 — 이 고지가 빠지면 사용자를 오해하게 만듭니다)
- 인식 정확도의 한계가 있고, **직전 답변은 직접 고칠 수 있다**는 것 (9절)

**`[결정 완료 D16]` 마이크 권한 요청 화면의 안내 문구로 고지합니다.** 별도 동의 체크박스는 두지 않습니다.
브라우저의 동작이지 우리 서비스의 처리가 아니므로 우리가 동의를 받을 주체가 아닙니다. 다만
"음성을 저장하지 않는다"를 사용자가 "내 목소리는 어디에도 안 간다"로 읽을 수 있으므로 오해를 방치하지
않습니다. 동의 절차를 두지 않는 이유는, 거부해도 대안이 텍스트 모드뿐이라 실질적 선택지가 아니고
텍스트 모드는 이미 1급 경로로 제공되기 때문입니다.
`docs/` 아래 개인정보 정책에 반영할지는 사람 소유 문서이므로 사용자 판단입니다.

## 7. 면접관 스트림 처리 — `<<<META>>>` 차단

### 7.1 계약 확인

`02_ai_architecture.md` 6.2절과 `02_ai_contracts.md` 3.2절이 원본이고 이 파이프라인은 **소비자**입니다.
재정의하지 않고 그대로 따릅니다.

- 청크는 문장 단위, 10~80자 (T6이 이 상한 덕을 본다)
- `<<<META>>>` **이후 텍스트는 TTS로도 화면으로도 절대 나가지 않는다** (M3)
- SSE 이벤트 4종: `utterance_chunk` / `utterance_done` / `session_notice` / `stream_error`
- 스트림 중단 시 확정 청크까지 서버가 저장 (M7)

### 7.2 부분 센티널 버퍼 보류 규칙 (서버 책임, 이 문서는 확인만)

`02_ai_contracts.md` 3.2절의 구현 요구를 그대로 적습니다.

> 델타 경계에서 `<<<M` 같은 조각이 TTS로 새는 것을 막기 위해, 서버는 버퍼 끝의 **최대 9자**
> (`<<<META>>>` 길이 − 1)를 **항상 보류**했다가 다음 델타와 합쳐 판정합니다.

**이 파이프라인이 여기에 거는 조건 두 가지:**

| 조건 | 이유 |
|---|---|
| 보류 9자는 **청크 확정 판정에도 동일하게 적용**되어야 한다. 즉 보류 중인 꼬리를 포함해 문장 종결을 판정하지 않는다 | 종결 문자 판정이 보류 꼬리를 무시하면 `...했습니다.<<<M` 상태에서 `...했습니다.`를 청크로 확정한 뒤, 다음 델타에서 센티널이 완성되면서 이미 발화된 텍스트를 되돌릴 수 없다 |
| **스트림 종료 시 남은 보류 9자의 처리** — `02_ai_contracts.md` 3.2절 **M8**을 따른다. 보류분이 센티널을 포함하면 센티널 처리, **센티널의 진부분 문자열(접두사)이면 그대로 발화로 flush**, 그 외도 flush. **버리는 경로는 없다.** flush 후에 `utterance_done`을 보낸다 | 이 규칙이 없으면 정상 발화의 마지막 몇 글자가 유실되거나(문장이 잘려 발화됨), 반대로 `<<<META` 조각이 TTS로 나간다. 스트림이 끝난 이상 뒤에 붙을 델타가 없어 접두사가 완성될 가능성은 0이므로, 버리면 반드시 마지막 글자 유실이 된다 |

**[전달: `vercel-platform-engineer`]** 위 두 조건이 SSE 라우트 구현에서 지켜져야 합니다.
특히 두 번째(스트림 종료 시 보류 잔여 처리)는 이 문서 초안 작성 시점에 계약에 없던 항목입니다.
**2026-09-09 리더 결정 D17로 `02_ai_contracts.md` 3.2절에 M8로 추가되었고, 위 표는 그 확정 규칙에 맞춰 갱신했습니다.**
초안에는 "접두사이면 버린다"로 적혀 있었으나 이는 M8과 정반대이므로 철회합니다. → 15절 불일치 #4 해소

### 7.3 클라이언트는 센티널을 모른다

클라이언트에 센티널 방어 코드를 **두지 않습니다.**

- 계약상 `utterance_chunk.text`에는 센티널이 **절대 포함되지 않습니다**(계약 3.5절).
- 클라이언트가 이중으로 필터링하면 서버의 누수가 조용히 가려져, 버그가 있어도 발견되지 않습니다.
- 대신 **개발·스테이징 빌드에서만** 청크에 `<<<`가 포함되면 콘솔 경고 + `session_events` 기록을 남깁니다.
  프로덕션에서는 필터링도 경고도 하지 않습니다. **가리지 말고 드러냅니다.**

### 7.4 청크 → TTS 큐 적재 (문장 단위 파이프라이닝)

```
utterance_chunk 수신 (seq=0)
  ├─▶ 화면에 텍스트 append          ← 즉시. 오디오를 기다리지 않는다
  └─▶ speechSynthesis.speak(u0)     ← 즉시. 첫 청크가 재생을 시작시킨다
                                       상태: thinking → speaking

utterance_chunk 수신 (seq=1..n)
  ├─▶ 화면에 텍스트 append
  └─▶ speechSynthesis.speak(un)     ← 큐 뒤에 붙는다. 앞 발화가 끝나면 자동 재생

utterance_done 수신
  └─▶ 큐가 비고 마지막 utterance의 onend가 오면 → speaking → listening
      (TTS를 쓰지 않는 경우 utterance_done 즉시 → listening)
```

**핵심은 seq=0을 받는 즉시 재생을 시작하는 것입니다.** 전체 응답을 기다리면 지연이 배가 되고
5초 예산이 깨집니다. `speechSynthesis`의 발화 큐가 이 파이프라이닝을 별도 구현 없이 제공합니다.

`seq` 순서 보장: SSE는 순서를 보존하지만, 안전을 위해 `seq`가 기대값과 다르면 작은 순서 버퍼에
보관했다가 순서대로 큐에 넣습니다. **오디오는 순서를 되돌릴 수 없으므로** 여기서만은 방어합니다.

|---|---|---|---|---|
| 발화 종료 감지(VAD) | **300ms** | **~50ms** | **여유 250ms** | 타이머 만료는 즉시 판정된다. 20ms 폴링 주기 + 렌더 1프레임. **단 8.2절의 t=0 정의 문제 있음** |
| STT 최종 전사 | **900ms** | **100~400ms** | **여유 500ms 이상** | `interimResults=true`로 전사 대부분이 **발화 중에 이미 완료**된다. `stop()` 후 최종 결과 확정만 남는다. 스킬 지침의 "streaming STT면 대부분 발화 중에 일어난다"와 일치 |
| TTS 첫 오디오 바이트 | **900ms** | 로컬 음성 **150~350ms** / 원격 음성 **700~1,500ms** | **조건부 충족** | `localService === true` 음성 선택 시 충분한 여유. **원격 음성만 있는 환경에서는 초과 가능** (T2) |
| **voice 계층 소계** | **2,100ms** | **로컬 음성 기준 300~800ms** | **1,300ms 이상 반환 가능** | |

**따라서 voice 계층은 배분된 2,100ms 중 최대 1,300ms를 LLM 쪽에 되돌려 줄 수 있습니다.**
`ai-interview-architect`가 이 여유를 (a) TTFT 예산 상향, (b) 입력 토큰 상한 완화,
(c) 전체 여유 확대 중 어디에 쓸지 결정하면 됩니다. **voice 계층이 임의로 재배분하지 않습니다.**

**다만 위 추정치는 V3(3.6절) 실측 전의 추정입니다.** 실측 후 이 표를 갱신하고 결과를 다시 전달합니다.

### 8.2 반드시 보고해야 할 것 — t=0 정의 불일치

**6.3절 표의 "발화 종료 감지(VAD) 300ms"는 t=0을 무엇으로 보느냐에 따라 의미가 완전히 달라집니다.**

- **정의 A (엔드포인트 확정 시점)**: 침묵 타이머가 만료되어 "턴 종료"가 확정된 순간. → 300ms 예산 충족, 합계 4,500ms
- **정의 B (사용자의 마지막 음절)**: 사용자가 실제로 말을 멈춘 순간. → 여기에 **침묵 임계값 3,000ms(또는 1,800ms)가 통째로 더해집니다.**

정의 B로 재면 사용자 체감은 **최대 7,500ms**입니다. 브리프 7절의 "답변 종료 → 다음 질문 발화까지 최대 5초"를
문자 그대로 읽으면 정의 B에 가깝고, **그 기준으로는 5초를 지킬 수 없습니다.**

**voice 계층의 입장: 이건 예산 초과가 아니라 정의의 문제이며, 임의로 임계값을 낮춰 해결하지 않습니다.**
침묵 임계값을 1초로 낮추면 5초는 지켜지지만 **면접 중 생각하는 사용자의 말을 끊습니다.** 그건 제품을 망칩니다.

**완화책 (구현에 포함)**

| # | 완화책 | 효과 |
|---|---|---|
| C1 | **카운트다운 예고**(4.4절). 남은 1,200ms 동안 원형 인디케이터로 "곧 마칩니다"를 보여준다 | 침묵 구간이 **대기가 아니라 사용자가 통제하는 시간**이 된다. 체감 지연에서 빠진다 |
| C2 | **"답변 완료" 버튼**(4.4절). 누르면 침묵 대기가 0이 된다 | 정의 B에서도 5초 달성. 익숙해진 사용자의 기본 경로가 된다 |
| C3 | **종결 어미 적응 임계값**(4.3절). 1,800ms | 정상 답변의 대다수에서 1.2초 단축 |
| C4 | **서버 프리워밍**: 침묵 1,200ms 시점(카운트다운 시작)에 컨텍스트 조립 요청을 미리 보낸다. LLM은 호출하지 않는다 | 6.3절의 "서버 전처리 150ms"를 임계 경로에서 제거 |

C4는 **LLM을 미리 호출하지 않습니다.** 사용자가 말을 이으면 프리워밍 결과를 버리면 되지만,
LLM을 부르면 무료 티어 호출을 헛되이 소모하고 취소된 호출이 쿼터를 먹습니다.

**[보고 — `ai-interview-architect` / 리더]** 5초 목표의 t=0을 **정의 A(엔드포인트 확정 시점)**로 명문화할 것을
요청합니다. 정의 B를 유지해야 한다면 침묵 임계값을 1초대로 낮춰야 하는데, 그건 4.1절의 비대칭 손실 때문에
**voice 계층이 동의하지 않습니다.** 대신 C1~C4로 체감 지연을 관리하는 UX 트레이드오프를 제안합니다.
어느 쪽이든 이 문서와 `01_state_machine.md` 6절, `02_ai_architecture.md` 6.3절을 함께 갱신해야 합니다.

### 8.3 예산 초과 시 UI 동작 (상태 머신 6절과 동일)

`thinking`이 길어지는 것은 예산이 깨졌다는 신호이고, 사용자에게 반드시 보여야 합니다.

| 경과 | 동작 |
|---|---|
| 400ms | `transcribing` 또는 `thinking` **표시 필수**. 무표시 침묵 금지 |
| 1,800ms | 첫 청크 미도착 시 지연 안내 준비 (계약 6.3절 "첫 청크 1,800ms") |
| 3,000ms | "조금만 기다려 주세요" 보조 문구 |
| 8,000ms | 지연 안내 + **"텍스트로 전환" 버튼 노출** (폴백 사다리 2단계와 동일 경로) |

## 9. 전사 정정이 파이프라인에 끼어드는 지점

`01_product_spec.md` 5절 결정: **직전 자기 발화만** 인라인 편집 가능.

### 9.1 위치

```
[listening] ──턴 확정──▶ [transcribing] ──서버 전송──▶ [thinking] ──청크──▶ [speaking] ──▶ [listening]
                              │                            │                    │
                              │                            └── 정정 가능 ───────┘
                              │                                                 │
                              └─ 정정 창 열림 (내 마지막 답변에 연필 아이콘)     └─ 다음 질문 발화가
                                                                                    끝나면 정정 창 닫힘
```

**정정 창이 열려 있는 구간**: 내 답변이 화면에 렌더된 순간부터, **다음 면접관 발화의 `utterance_done`이
도착할 때까지**. 그 이후에는 그 답변을 근거로 이미 꼬리질문이 만들어졌으므로 닫힙니다(제품 스펙 5절).

`thinking` 구간(면접관이 생각하는 몇 초)이 정정을 하기에 가장 자연스러운 지점입니다.
사용자는 어차피 기다리고 있고, 자기 전사를 방금 읽었습니다. **지연이 UX 손실이 아니라 정정 기회가 됩니다.**

**단, 정정이 이미 전송된 답변을 소급해 바꾸지는 않습니다.** 면접관은 정정 전 텍스트로 이미 질문을
만들고 있습니다. 정정의 목적은 **평가 인용의 정확성**(핵심 가치 2)이지 꼬리질문의 수정이 아닙니다.
이 점을 UI 문구에 반영해야 합니다 — "고친 내용은 평가에 반영됩니다"이지 "면접관이 다시 듣습니다"가 아닙니다.

### 9.2 데이터 흐름

| 시점 | `transcript_text` | `transcript_raw` | `is_corrected` | `stt_confidence` |
|---|---|---|---|---|
| 최초 커밋 (voice) | STT 최종 전사 | `NULL` | `false` | 0~1 또는 `NULL` (L6) |
| 최초 커밋 (text) | 사용자 입력 | `NULL` | `false` | `NULL` |
| 정정 후 | **사용자 수정본** | **STT 원문**(최초 `transcript_text`를 여기로 이동) | `true` | 변경 없음 |

`04_data_layer.md`의 `turns_correction_shape` CHECK(`is_corrected = true`면 `transcript_raw is not null`
그리고 `role = 'candidate'`)를 이 흐름이 만족합니다. **정합 확인 완료.**

정정은 `turns`에 클라이언트 쓰기 정책이 없으므로(`04_data_layer.md` 6절) **반드시 API 라우트를 경유**합니다.
`vercel-platform-engineer`에게 `PATCH /api/sessions/[sessionId]/turns/[turnId]` 계열 라우트가 필요합니다.

### 9.3 정정을 유도하는 신호

`stt_confidence`가 낮게 기록된 발화(예: `< 0.6`)에는 화면에 **"인식이 불확실합니다. 확인해 주세요"** 힌트를
붙입니다. L6 때문에 값이 `NULL`인 경우가 많을 것이므로 이건 **보조 신호이지 주 수단이 아닙니다.**
정정 버튼 자체는 confidence와 무관하게 항상 노출됩니다.

## 10. 모달리티 전환

### 10.1 원칙

- **전환은 상태 전이가 아닙니다.** `in_progress` 안의 자기 전이이고 세션은 끊기지 않습니다
  (`01_state_machine.md` 2절·5절).
- **양방향입니다.** 텍스트 → 음성 복귀도 언제든 허용됩니다. 자동 전환된 사용자가 문제를 고친 뒤
  음성으로 돌아올 수 있어야 합니다.
- **대화 로그는 하나입니다.** 어느 모드에서 만들어졌든 `turns` 한 테이블에 시간순으로 쌓입니다.
  평가 파이프라인은 모달리티를 구분하지 않습니다.

### 10.2 전환 경로 매트릭스

| 계기 | 감지 | 자동/수동 | `current_modality` | `turns.modality` | `session_events` | 사용자에게 보이는 것 |
|---|---|---|---|---|---|---|
| **마이크 권한 거부** | `getUserMedia`가 `NotAllowedError`로 reject | **자동** (`voice → text`) | `'text'` | 이후 턴은 `'text'` | `modality_switched`, detail `{reason:'mic_permission_denied'}` | "마이크 권한이 거부되었습니다. 텍스트로 이어서 진행합니다" + 권한 재요청 안내 |
| **마이크 하드웨어 실패 / 장치 없음** | `NotFoundError`·`NotReadableError`·`OverconstrainedError`, 또는 세션 중 트랙 `ended` 이벤트 | **자동** | `'text'` | `'text'` | detail `{reason:'mic_unavailable'}` | "마이크를 사용할 수 없습니다. 텍스트로 이어서 진행합니다" + 장치 재선택 |
| **브라우저 STT 미지원** | 3.6절 사전 점검 2번 | **자동, 세션 시작 전** | 시작부터 `'text'` | `'text'` | 세션 시작 이벤트 detail | "이 브라우저는 음성 인식을 지원하지 않습니다. 텍스트 면접으로 진행합니다" |
| **STT 연속 실패** | `onerror` 또는 재시작 실패가 **연속 3회** (4.4절) | **자동** | `'text'` | `'text'` | detail `{reason:'stt_error', errorCode}` | "음성 인식에 반복해서 실패했습니다. 텍스트로 이어서 답변해 주세요" |
| **STT 결과 없음(1회)** | 최종 전사가 빈 문자열 | **전환 안 함** | 변화 없음 | — | — | "잘 들리지 않았습니다. 다시 말씀해 주세요" + 텍스트 입력창도 함께 열어 둠 |
| **레이트 리밋 / 프로바이더 불가 — STT** | 폴백 사다리 2단계 (3.4절 재해석) | **자동** | `'text'` | `'text'` | detail `{reason:'rate_limit_fallback', layer:'stt'}` | "마이크 인식이 잠시 불가합니다. 텍스트로 이어서 답변해 주세요" (상태 머신 4절 문구) |
| **레이트 리밋 / TTS 불가** | 폴백 사다리 1단계 | **자동, 부분 전환** | **변화 없음 (`'voice'` 유지)** | 사용자 발화는 계속 `'voice'` | detail `{reason:'rate_limit_fallback', layer:'tts'}` | "지금은 면접관 목소리 없이 텍스트로 진행합니다" |
| **`thinking` 8초 초과** | 8.3절 타이머 | **수동** (버튼 노출) | 누르면 `'text'` | `'text'` | detail `{reason:'user_requested_after_delay'}` | 지연 안내 + "텍스트로 전환" 버튼 |
| **사용자 수동 전환** | 토글 클릭 | **수동** | `'text'` ↔ `'voice'` | 해당 턴부터 | detail `{reason:'user_requested'}` | 즉시 전환 |
| **텍스트 → 음성 복귀** | 토글 클릭 | **수동** | `'voice'` | `'voice'` | detail `{reason:'user_requested'}` | 마이크 재점검(3.6절 3·5번) 후 전환. 실패하면 텍스트 유지 |

### 10.3 전환의 원자성 — 순서가 중요합니다

전환 도중 발화가 유실되면 안 됩니다.

```
voice → text 전환:
  1. 진행 중인 턴이 있으면 → 지금까지의 interim 전사를 텍스트 입력창에 미리 채운다  ← 유실 방지
  2. releaseAudioGraph()  (6.2절)
  3. current_modality = 'text' 서버 반영 + session_events 기록
  4. 텍스트 입력창 포커스
  5. 상태: * → text_fallback → (입력 대기)

text → voice 전환:
  1. 입력창에 미제출 텍스트가 있으면 → 전환을 막고 "먼저 제출하거나 지워 주세요" 안내
  2. 3.6절 점검 3·5번 재실행 (실패하면 여기서 중단, 텍스트 유지)
  3. 오디오 그래프 구성 + SpeechRecognition 시작
  4. current_modality = 'voice' 서버 반영 + session_events 기록
```

**1번(interim 전사 이월)이 이 절의 핵심입니다.** 사용자가 30초를 말했는데 STT가 죽어서 전환됐을 때
그 내용이 사라지면, 사용자는 처음부터 다시 답해야 합니다. 그건 세션을 죽이는 것과 체감이 같습니다.
불완전한 전사라도 입력창에 남겨 두면 사용자가 고쳐서 제출할 수 있습니다.

### 10.4 접근성 — 텍스트만으로 완전한 면접

**텍스트 모드가 음성 모드의 열화판이어서는 안 됩니다.** `01_state_machine.md`·`01_product_spec.md`가
음성 없이도 전 기능을 요구하므로, 이 계층은 다음을 보장합니다.

| 보장 | 내용 |
|---|---|
| **기능 동등** | 텍스트 모드에서 사용할 수 없는 면접 기능이 **하나도 없다.** 꼬리질문, 압박, 종료 조건, 평가, 리포트, 정정 전부 동일 |
| **평가 동등** | 평가 파이프라인은 `turns.transcript_text`만 읽고 `modality`를 채점에 쓰지 않는다. **텍스트로 봤다고 점수가 불리해지지 않는다** |
| **시작 경로 동등** | `/sessions/new`에서 텍스트 모드를 **처음부터** 선택할 수 있다. 음성을 시도했다가 실패해야만 갈 수 있는 경로가 아니다 |
| **상태 표시 동등** | `thinking`/`speaking`은 텍스트 모드에서도 그대로 표시된다(오디오만 없다). 면접관이 응답 중이라는 사실은 모달리티와 무관하게 보여야 한다 |
| **스크린 리더** | 상태 변화와 새 발화는 `aria-live` 영역으로 알린다. **상태를 색이나 애니메이션만으로 표현하지 않는다.** 반드시 텍스트 레이블을 동반한다 |
| **키보드 전용** | "답변 완료", "일시정지", "텍스트로 전환", "정정"이 전부 키보드로 도달 가능. 음성 모드에서도 마찬가지 |
| **청각 접근성** | 면접관 발화는 **항상 화면에 텍스트로 먼저** 나타난다(❻이 ❼보다 앞). TTS는 부가물이다 |

**전달 — `shadcn-ui-engineer`**: 위 7개 항목은 UI 구현에서 검증 대상입니다.
특히 "상태를 색만으로 표현하지 않는다"와 "텍스트가 오디오보다 먼저"는 놓치기 쉽습니다.

## 11. UI 상태 계약 (`shadcn-ui-engineer`와 문자 단위 동일)

### 11.1 정본 4상태

`01_state_machine.md` 6절이 정의한 4개가 계약입니다. **아래를 문자 그대로 복사해 쓰십시오.**

```
listening
transcribing
thinking
speaking
```

### 11.2 상태별 규약

| 상태 | 의미 | 진입 | 이탈 | 한국어 표시(초안) | 타이머 |
|---|---|---|---|---|---|
| `listening` | 사용자의 발화를 기다리거나 듣는 중 | 면접관 발화 종료, barge-in, 세션 시작 | 턴 확정 | "듣는 중" + VU 미터 + "답변 완료" 버튼 | 침묵 카운트다운(4.3절) |
| `transcribing` | 발화가 끝나고 전사를 확정하는 중 | 턴 확정(t=0) | 서버 전송 완료 | "받아쓰는 중" | **t+400ms 이내 표시 필수** |
| `thinking` | 면접관이 응답을 만드는 중 | 서버 전송 완료 | 첫 `utterance_chunk` 도착 | "면접관이 생각 중" | 3초 → 보조 문구 / 8초 → 전환 버튼 |
| `speaking` | 면접관 발화 재생 중 | 첫 청크 도착 | TTS 큐 소진 + `utterance_done` (또는 TTS 미사용 시 `utterance_done` 즉시) | "말하는 중" | — |

**`transcribing`은 텍스트 모드에서 나타나지 않습니다.** 텍스트 모드는 제출 즉시 `thinking`으로 갑니다.
나머지 3개는 두 모달리티 모두에서 나타납니다.

### 11.3 4상태로 표현되지 않는 것

`voice-text-dual-modality` 스킬은 `idle` / `requesting_permission` / `error` / `text_fallback`을 포함한
8상태를 제안합니다. 이 프로젝트는 **`01_state_machine.md` 6절의 4상태를 정본 계약으로 삼되**,
아래 4개를 **보조 상태**로 둡니다. 이들은 면접 대화 루프 밖(준비 화면·오류 배너·모드 표시)에 속하며,
`shadcn-ui-engineer`와 별도 합의가 필요합니다.

```
idle
requesting_permission
error
text_fallback
```

- `idle` — `ready` 화면. 아직 면접이 시작되지 않음
- `requesting_permission` — `getUserMedia` 권한 프롬프트 표시 중 (`ready` 화면 점검 단계)
- `error` — 복구 가능한 음성 오류 배너. **면접 루프를 멈추지 않는 오버레이**이며 4상태와 동시에 존재할 수 있음
- `text_fallback` — 텍스트 모드로 전환됨을 알리는 표시. 실제로는 `current_modality === 'text'`의 UI 표현

**[전달: `shadcn-ui-engineer`]** 4상태는 계약이므로 이름을 바꾸지 마십시오. 보조 4개는 UI 소유 영역이라
이름을 조정하고 싶으면 알려 주시고, 확정되면 이 절과 UI 문서를 함께 갱신합니다.
`error`를 **4상태와 배타적인 상태로 만들지 마십시오** — 배타적으로 만들면 오류 중에 `thinking`이 사라져
면접관이 응답 중인지 알 수 없게 됩니다.

## 13. 레이트 리밋 폴백 사다리에서 음성 계층의 역할

`01_state_machine.md` 4절이 원본입니다. 이 절은 각 단계에서 **음성 계층이 실제로 무엇을 하는지**만 적습니다.

| 단계 | 리밋 주체 | 음성 계층의 동작 | 음성 계층이 하지 않는 것 |
|---|---|---|---|
| **1** | TTS | `speechSynthesis.cancel()` + 세션 내 TTS 플래그 `off`. **마이크와 STT는 그대로 유지.** `current_modality`를 건드리지 않는다 | 상태 전이 요청을 하지 않는다. 사용자 입력 모드를 바꾸지 않는다 |
| **2** | STT | `releaseAudioGraph()` 실행 → interim 전사를 입력창으로 이월(10.3절) → `current_modality = 'text'` 반영 요청 → `session_events` 기록 | 상태 전이 요청을 하지 않는다(`in_progress` 유지가 계약). **TTS는 끄지 않는다** — 면접관 음성은 계속 나올 수 있다 |
| **3** | LLM (일시) | `thinking` 유지. 3초 보조 문구, 8초 텍스트 전환 버튼(8.3절). **오디오 그래프를 해제하지 않는다** (곧 재개될 것이므로 마이크를 다시 잡는 비용을 피한다) | 재시도를 하지 않는다. 백오프는 서버 책임 |
| **4** | LLM (초과) | `releaseAudioGraph()` **필수**. 일시정지 화면 진입 | 상태 전이를 스스로 하지 않는다. 서버가 `paused`로 옮긴 것을 받아 반응한다 |

**핵심 비대칭 두 가지 (설계 의도)**

1. **1단계와 2단계는 독립입니다.** TTS가 죽어도 사용자는 음성으로 답할 수 있고, STT가 죽어도
   면접관 목소리는 나옵니다. 이걸 한 덩어리로 묶으면 멀쩡한 절반을 버리게 됩니다.
2. **3단계는 오디오 그래프를 유지하고 4단계는 해제합니다.** 3단계는 초 단위 대기라 마이크를 다시
   잡는 비용(권한 확인·장치 초기화·노이즈 플로어 재학습)이 대기보다 큽니다. 4단계는 최소 수 시간
   ~다음 날이라 마이크 표시등을 켜 둘 이유가 전혀 없습니다.

**3.4절의 재해석을 다시 강조합니다.** 브라우저 내장 API를 쓰므로 1·2단계의 계기는 "우리 쿼터 소진"이
아니라 **"브라우저가 제공하는 기능의 일시적 불가"**(F7·F10~F12)입니다. 사다리의 **동작은 동일**하고
**계기의 이름만 다릅니다.** → 15절 불일치 #1

| U8 | 음성 고지 문구 4가지(6.4절)를 `ready` 화면에 넣어 주십시오. 특히 **브라우저가 음성을 제조사 서버로 보낼 수 있다**는 항목이 빠지면 안 됩니다 |
