## 1. 한 줄 정의와 MVP 범위

> IT 직군 경력자가 이력서와 JD를 넣고 **심층 압박형 / 기술 검증형** 중 하나를 골라
> **음성으로 모의면접**을 치른 뒤, **답변 원문이 인용된 평가 리포트**를 받는다.

MVP에서 마지막까지 남는 셋: **이력서를 읽은 꼬리질문 / 원문 인용 평가 / 음성 대화.**

## 2. 네이밍 규칙 (전 팀 공통 — 경계 불일치의 유일한 예방책)

```
DB (Postgres)  : snake_case   예) session_id, created_at, main_question_budget
API 응답        : camelCase    예) sessionId, createdAt, mainQuestionBudget
프론트 타입      : camelCase (API 응답과 동일)
변환 시점        : API 라우트에서 단 한 번. 프론트에서도, DB 레이어에서도 변환하지 않는다.
```

- status enum 값(`in_progress` 등), 루브릭 축 식별자(`job_knowledge` 등), 라우트 경로는
  **camelCase로 바꾸지 않고 문자열 그대로** 오갑니다. 이들은 필드명이 아니라 값이기 때문입니다.
- 문서 서술은 한국어, 그 안의 식별자는 영어입니다. status 값이나 컬럼명을 한국어로 번역하면
  CHECK 제약과 API 계약이 깨집니다.

## 5. 전사 오류 정정 (브리프 9절 #3 결정)

**결정: 정정 기능을 넣되, 범위를 "직전 자기 발화"로 제한한다.**

- 면접 중, 사용자는 **자기 마지막 답변** 한 건만 인라인 편집할 수 있습니다. 다음 질문이 나온 뒤에는
  그 답변을 더 이상 고칠 수 없습니다(그 답변을 근거로 이미 꼬리질문이 만들어졌기 때문).
- 정정 시 STT 원문은 `turns.transcript_raw`에 보존하고, `transcript_text`가 수정본이 됩니다.
  이후 모든 질문 생성과 평가·인용은 `transcript_text`를 씁니다. `is_corrected = true`로 표시합니다.
- 면접관(AI) 발화는 편집 불가입니다.
- 리포트 화면에서는 편집 대신 **이의 제기**로 처리합니다(`reason_code = 'transcription_error'`).
  MVP에서 이의 제기는 재평가를 유발하지 않고 데이터만 수집합니다. `[later]`로 재평가 연결.

**근거.** 음성 원본을 저장하지 않으므로 전사가 평가 근거의 유일한 원천이고(브리프 7절),
무료 티어 STT는 정확도가 낮습니다(7절 함의 4). 정정 수단이 없으면 잘못된 인용이 리포트에 남아
핵심 가치 2번이 무너지고 이의 제기율(지표 5)만 올라갑니다. 반대로 전체 로그를 자유 편집하게 하면
사후 답변 미화가 가능해져 회차 간 비교(핵심 가치 3번)가 무의미해지고, 이미 생성된 꼬리질문과
로그가 어긋납니다. "직전 발화만"이 두 위험 사이의 최소 지점입니다.

## 6. 이력서·JD 텍스트 추출 (브리프 9절 #5 — 초안 결정)

**초안 결정: 서버(Next.js Route Handler, Node.js 런타임)에서 추출한다.** 최종 확정은 `vercel-platform-engineer`.

| 방안 | 판단 |
|---|---|
| 클라이언트 파싱 | 기각 — PDF 파서가 번들을 크게 키우고 브라우저·기기별 결과 편차가 생김. 결과 재현이 어려움 |
| **서버 파싱** | **채택** — 무료 티어 안에서 처리 가능(추가 과금 $0), 텍스트 정규화 규칙을 한 곳에서 관리, 실패를 서버 로그로 추적 |
| LLM에 파일 직접 투입 | 기각 — 무료 티어 토큰을 크게 소모하고 프로바이더 파일 API에 종속됨. 예산 제약 위반 |

- 흐름: 업로드 → Storage 저장 → 서버에서 텍스트 추출 → `documents.extracted_text` 저장 →
  `extraction_status`를 `succeeded` / `failed`로 기록.
- 추출 결과는 사용자에게 **보여주고 편집 가능하게** 합니다. 추출 품질이 질문 품질을 좌우하므로
  사용자가 확인 없이 넘어가면 안 됩니다.
- 텍스트 레이어가 없는 스캔 PDF는 MVP에서 `failed`로 처리하고 텍스트 직접 입력을 안내합니다. OCR은 `[later]`.
- 파일 크기 상한 10MB, 허용 확장자 `pdf` / `docx` / `txt` / `md`.

## 6.5 AI 키 연결(BYOK)과 체험 세션 (D28·D29)

### 6.5.1 한 문장 요약

> **첫 면접은 키 없이 공용으로 돌린다. 리포트를 본 직후에 본인 키를 요구한다.
> 그 다음부터는 본인 키로 돈다.**

D27의 예약 게이트는 버려지지 않고 **역할이 좁아집니다 — 이제 체험 세션만 배급합니다.**
본인 키를 연결한 사용자는 공용 여력과 무관하게 언제든 면접을 시작할 수 있습니다.
예약·반납 메커니즘은 `02_ai_architecture.md` 8.3절이 원본이고, 그 게이트가 걸리는 전이와 가드는
`01_state_machine.md` 2절이 원본입니다.

### 6.5.2 온보딩 순서 — 가치를 먼저 보여주고 그 다음에 요구한다

키 연결은 온보딩에 마찰을 하나 더 얹습니다. 타깃이 면접 D-7의 급한 사용자이므로 이 마찰은 가볍지
않고, **순서로 방어합니다.**

```
가입 → 세션 설정 → [체험 동의] → 체험 면접 → 리포트 → [키 연결 요구] → 재시도(본인 키)
                     (D29)                        ↑ 여기가 요구 지점
```

| 지점 | 키를 요구하지 않는 이유 / 요구하는 이유 |
|---|---|
| 가입 직후 | **요구하지 않는다.** 아직 제품을 본 적이 없다. 여기서 키를 물으면 이탈이 곧 전부다 |
| 세션 설정 화면 | **요구하지 않는다.** 이력서·JD를 채우는 것 자체가 이미 큰 투자다. 두 마찰을 겹치지 않는다 |
| 면접 도중 | **절대 요구하지 않는다.** 진행 중인 면접을 인질로 삼는 구조가 된다 |
| **리포트 열람 직후** | **요구한다.** 사용자가 방금 가치를 확인했고, 재시도 의사가 가장 높은 순간이다. 북극성 지표(지표 3 재시도율)의 측정 지점과 정확히 겹친다 |
| 두 번째 세션 시작 시도 | **차단 지점.** 이때는 요구가 아니라 이미 안내받은 것의 확인이다 |

**리포트 화면의 키 CTA 요구사항**
- 리포트 본문(점수·인용·개선점)을 **가리지 않습니다.** 사용자가 리포트를 다 읽고 난 하단,
  "같은 이력서로 다시 하기" 버튼과 **같은 카드 안**에 둡니다. 두 CTA가 경쟁하면 북극성 지표가 깎입니다.
- 문구는 제약이 아니라 업그레이드로 씁니다(6.5.4절의 프라이버시 근거가 여기서 회수됩니다).
- 닫을 수 있어야 하고, 닫아도 대시보드와 세션 목록에 조용한 안내가 남습니다.
- **키를 이미 연결한 사용자에게는 이 카드가 아예 렌더되지 않습니다.**

### 6.5.3 세션의 재원과 사용자에게 보이는 상태

세션은 시작 시점에 **어느 키로 도는지**가 확정되고, 세션이 끝날 때까지 바뀌지 않습니다.
값 목록과 전이 가드는 `01_state_machine.md` 1·2절이 원본입니다.

| `funding_source` | 의미 | 예약 게이트 | 키 |
|---|---|---|---|
| `trial_shared` | 체험 세션. 서비스 공용 키로 진행 | **적용됨**(D27) | 없음 |
| `byok` | 사용자가 연결한 본인 키로 진행 | **적용되지 않음** | 사용자 키 |

사용자에게 보이는 키 상태는 셋뿐입니다(내부 값은 영어, 표시는 한국어).

| `keyStatus` | 사용자에게 보이는 문구 | 무엇을 할 수 있나 |
|---|---|---|
| `none` | "연결된 키 없음" | 체험이 남아 있으면 체험 가능. 아니면 키 연결만 |
| `connected` | "연결됨 · ****{끝 4자리}" | 언제든 면접 시작 |
| `invalid` | "키를 다시 확인해 주세요" | 키 교체 후 재개 |

- 체험 소진 여부는 `trialStatus`(`available` / `consumed`)로 표현합니다.
  **화면에 "1/1", "남은 횟수", "무료 체험 잔여" 같은 카운터를 노출하지 않습니다** — 그 순간
  제품이 요금제처럼 보입니다. 체험은 "첫 면접"이지 "무료 쿠폰"이 아닙니다.

### 6.5.4 체험 세션의 데이터 처리 동의 (D29)

체험 세션은 **우리 키로, 사람이 읽을 수 있는 환경에** 사용자의 이력서와 답변을 보냅니다.
숨기지 않고 시작 전에 그대로 말하고 동의를 받습니다.

**동의 시점:** 세션 설정을 마치고 준비를 시작하기 직전(`configuring → ready` 전이의 가드).
그 전이가 세션의 첫 AI 호출(플래너)을 일으키므로, 그보다 앞서야 하고 그보다 이를 필요도 없습니다.

**동의 문구(초안 — 이 문장을 그대로 씁니다).**

> **체험 면접을 시작하기 전에 확인해 주세요**
>
> 체험 면접은 Google의 무료 AI 서비스로 진행됩니다. 입력하신 이력서와 답변을 Google이 서비스
> 개선에 사용할 수 있고, 검토자가 읽을 수 있습니다.
> 본인 API 키를 연결하면 이 과정을 거치지 않습니다.
>
> `[동의하고 시작하기]`  `[내 키를 연결할게요]`

**규칙**
- 기본값은 **체크되지 않은 상태**입니다. 미리 동의시켜 두지 않습니다.
- **거부는 막다른 길이 아닙니다.** "내 키를 연결할게요"를 누르면 `/settings/api-key`로 이동하고,
  돌아오면 같은 세션 설정이 그대로 남아 있습니다(세션은 `configuring`에 머뭅니다).
- **동의 사실과 시각을 기록합니다.** 스키마는 `supabase-engineer`가 정하되, 요구사항은
  (a) 누가, (b) 언제, (c) 어떤 문구 버전에 동의했는지 셋을 남기는 것입니다. 문구를 고치면
  버전이 올라가고, 과거 동의 기록은 과거 문구를 가리켜야 합니다.
- 동의는 **체험에만** 필요합니다. `funding_source = 'byok'` 세션은 이 화면을 보지 않습니다 —
  본인 계정에서 본인 데이터에 대해 본인이 동의한 구조이기 때문입니다.
- 이 화면은 D16(브라우저 STT가 음성을 외부로 보낼 수 있다는 마이크 권한 화면의 안내)과 **별개**입니다.
  둘을 한 화면에 합치지 마세요. 주체도 다르고 시점도 다릅니다.

### 6.5.5 막혔을 때의 출구 — D28의 핵심 이득

D27만 있었을 때 여력이 없는 사용자에게 할 수 있는 말은 "오늘은 여기까지"뿐이었습니다.
D28 이후에는 **출구가 있습니다.** 같은 벽인데 다른 경험이고, 이것이 BYOK를 도입한 이유입니다.

**규칙: 여력 부족 안내에는 반드시 키 연결 경로가 함께 있어야 합니다.**

> **지금은 새 면접을 시작할 수 없어요**
> 오늘 진행할 수 있는 면접이 모두 찼습니다.
> **본인 API 키를 연결하면 지금 바로 시작할 수 있어요.**
> 이미 진행 중인 면접과 지난 리포트는 그대로 보실 수 있습니다.
>
> `[키 연결하기]`  `[지난 리포트 보기]`

- **1순위 버튼은 "키 연결하기"입니다.** "확인"이 1순위이면 사용자는 그냥 나갑니다.
- "내일 다시 오세요"를 **유일한 안내로 두지 마세요.** 시각 안내는 부차 정보로 내립니다.
- 체험을 이미 쓴 사용자에게는 여력과 무관하게 같은 화면을 보여줍니다 — 벽의 이유가
  "오늘 자리 없음"이든 "체험 사용함"이든 사용자가 할 일은 하나로 같습니다.
- `02_ai_architecture.md` 13.6.3절의 금칙어 목록이 그대로 적용됩니다:
  **"무료 티어", "한도", "쿼터", "quota", "레이트 리밋", "RPD", "API 한도", "예약분", "토큰" 금지.**
  (연결할 대상인 "API 키"라는 말은 씁니다 — 사용자가 Google에서 발급받을 것의 이름이기 때문입니다.)

### 6.5.6 사용자 키가 실패할 때 — 우리 한도가 아니다

체험 세션이 막히는 것과 **사용자 키가 막히는 것은 다른 사건**입니다. 원인도 복구 주체도 다르므로
안내 문구와 복구 경로를 분리합니다. 상태 전이는 `01_state_machine.md` 2절·4.5절이 원본입니다.

| 사건 | 원인 주체 | 사용자에게 보이는 것 | 복구 |
|---|---|---|---|
| 공용 여력 소진 | **우리** | "오늘 진행할 수 있는 면접이 모두 찼습니다" + 키 연결 CTA | 키 연결 또는 다음 날 |
| 사용자 키가 유효하지 않음 | **사용자** | "연결하신 키로 접속할 수 없었어요. 키가 삭제되었거나 권한이 바뀌었을 수 있습니다" | 키 교체 → "이어서 하기" |
| 사용자 키의 한도 소진 | **사용자** | "연결하신 키의 사용량이 오늘 한도에 도달했어요. Google AI Studio에서 확인하실 수 있습니다" | 다음 날 또는 결제 활성화 → "이어서 하기" |

- **면접 도중에 발생하면 세션을 잃지 않습니다.** `paused`로 보존되고 대화 로그는 그대로입니다.
  키를 고친 뒤 "이어서 하기"를 누르면 마지막 질문부터 계속됩니다.
- 사용자 키 실패에는 **"내일 다시 오세요"를 쓰지 마세요.** 우리가 정한 시각이 아니라 사용자
  계정의 상태이므로, 우리는 언제 풀리는지 알 수 없습니다. 확인할 곳을 알려주는 것이 정확합니다.
- 이 안내에서만 예외적으로 사용자 키의 "한도"를 언급합니다 — 그것은 우리 내부 사정이 아니라
  **사용자 본인 계정의 사실**이고, 그것을 감추면 사용자가 원인을 찾을 수 없습니다.
- 사용자 키가 실패했을 때 **공용 키로 조용히 넘어가지 않습니다.** 동의(D29)를 받지 않은 데이터가
  공용 경로로 나가게 되고, 사용자가 그 사실을 모르게 됩니다.

### 6.5.7 보안 요구사항 (D28 — 타인의 자격증명을 보관하는 책임)

구현은 `supabase-engineer`·`vercel-platform-engineer` 몫이지만, **제품 요구사항으로 못 박습니다.**

1. **저장 시 암호화 필수**(Supabase Vault). RLS만으로 부족합니다.
2. **클라이언트로 원문을 절대 되돌려주지 않습니다.** 어떤 API 응답에도 키 원문 필드를 두지 않고,
   마스킹된 끝 4자리만 노출합니다. "수정" 동작은 **조회 후 편집이 아니라 전체 교체**입니다.
3. **복호화는 서버에서만** 일어나고, 키는 `NEXT_PUBLIC_` 계열 어디에도 닿지 않습니다.
4. **계정 삭제 시 키도 실제 삭제**됩니다(브리프 7절 삭제 정책과 동일 — 소프트 삭제 아님).
   키 해제(연결 끊기)도 마찬가지로 실제 삭제입니다.
5. 키는 **로그·오류 메시지·이벤트 페이로드에 남지 않습니다.** 프로바이더 오류를 그대로 노출하지 말고
   6.5.6절의 세 분류로 정규화해서 보여줍니다.
6. 키 연결·교체·해제는 `session_events`가 아니라 **계정 계열 감사 로그**에 남깁니다
   (`session_events`는 지표 1·2의 원천 테이블이라 오염시키지 않습니다).

### 6.5.8 이 결정이 뒤집히는 조건

체험 1회가 재시도 의사를 만들기에 부족하다는 증거가 나오면 — 구체적으로 **지표 3(재시도율)이
베이스라인 대비 키 요구 도입 후 크게 떨어지면** — 체험 횟수를 늘리는 것이 첫 번째 조정 레버입니다.
`02_ai_architecture.md` 8.3.8절대로 체험 예약량이 전부 환경변수이므로 코드 변경 없이 조정됩니다.

### 리포트 화면의 피드백 수집 UI (지표 4·5 — 필수)

1. **유용성 피드백** (지표 4): 리포트 하단 "이 피드백이 도움이 되었나요?" — 도움됨 / 도움 안 됨 + 선택 코멘트.
   세션당 1회 저장, 수정 가능. `report_feedback`에 기록.
2. **항목별 이의 제기** (지표 5): 각 축 점수 카드와 각 인용문 옆에 "이건 아닌 것 같아요".
   사유 코드를 고르게 합니다 — `transcription_error`(제 말과 다름) / `misinterpreted`(의도를 잘못 읽음) /
   `score_too_low`(점수가 부당함) / `other`. `score_disputes`에 기록.
   지표 5는 "축 점수 카드 노출 대비 클릭 비율"로 계산하므로 카드 노출 이벤트도 남깁니다.

### 키 연결 화면을 `/settings/account`에 넣지 않고 별도 라우트로 뺀 근거

**결정: `/settings/api-key`를 신설한다.** 네 가지 이유입니다.

1. **이 화면은 설정이 아니라 온보딩의 마지막 단계입니다.** 리포트 하단 CTA, 여력 부족 안내,
   대시보드 배너, 동의 거부 경로 — 최소 네 곳에서 딥링크로 들어옵니다. 진입 후 원래 하려던 일로
   돌아가야 하므로 `?next=`를 받는 **자기 라우트**가 필요합니다. `/settings/account#api-key`
   앵커로는 복귀 경로를 표현할 수 없고, 계정 화면 전체를 로드한 뒤 스크롤되는 경험이 됩니다.
2. **`/settings/account`의 주 기능은 계정 삭제입니다.** 신규 사용자가 가장 자주 가야 할 화면과
   가장 비가역적인 버튼을 같은 페이지에 두지 않습니다.
3. **설명해야 할 내용이 짧지 않습니다.** 키 발급 방법, 결제를 활성화한 키와 무료 키의 차이(D29),
   보관 방식과 삭제 정책 — 계정 화면의 한 섹션에 밀어 넣으면 양쪽 모두 읽히지 않습니다.
4. **중복 구현을 막습니다.** `/settings/account`에는 상태 한 줄과 링크만 두고, 연결·교체·해제
   폼은 이 라우트에만 존재합니다. 폼이 두 곳에 있으면 6.5.7절의 보안 규칙도 두 곳에서 검증해야 합니다.

`/onboarding/...` 같은 별도 온보딩 네임스페이스는 두지 않습니다 — 첫 연결 이후에도 교체·해제로
계속 쓰이는 화면이라 온보딩 전용이 아닙니다.

## 8. 범위 밖 (하지 않을 것)

브리프 6절 Non-goals를 그대로 따릅니다: 화상·표정 분석, 공유·랭킹·커뮤니티, 결제·구독,

- 경험 탐색형 페르소나와 신입 타깃 흐름
- 데일리 연습·스트릭 등 상시 리텐션 기능 (브리프 3절: 유입이 산발적이라는 정의와 어긋남)

- 팀·조직 계정, 초대
- 알림 이메일 (리포트 완료 알림은 앱 내 배지로만)
- **키 대납·결제 대행·크레딧 판매.** 우리는 사용자 키를 중계할 뿐 과금 주체가 되지 않습니다

- **키 사용량·잔여 한도 조회 화면.** Google AI Studio 무료 티어에 잔여량 조회 경로가 없고

- **Gemini 외 프로바이더 키 지원**(D11 — Google 단독). 추상화 계층은 유지하므로 `[later]`

## 9. 결정 완료

남은 미결 없음. (2026-09-09)

**D2 — 리포트 완료 알림은 앱 내 배지만.** 이메일을 보내지 않습니다.
무료 티어 기본 SMTP는 시간당 발송 한도가 낮아 외부 프로바이더가 필요해지고, 이는 "무료 티어 안에서
해결"이라는 예산 제약과 충돌합니다. 평가가 1~2분이면 사용자가 대기 화면에 머물 가능성이 높아 손실이
작습니다. 먼저 지표 2(리포트 도달률)의 베이스라인을 보고 다시 판단합니다.

**D4 — 이의 제기(지표 5)는 수집만 하고 재평가를 유발하지 않습니다.**
무료 티어 호출을 추가로 쓰지 않고 구현이 단순합니다. 다만 사용자가 "눌러도 아무 일 없음"으로 느낄 수
있으므로, 이의 제기 후 **접수되었다는 확인과 그 사유가 다음 개선에 쓰인다는 안내**를 UI에 반드시
노출해야 합니다. 이것이 없으면 지표 5 자체가 수집되지 않습니다.

**D1 — 총점은 숫자로 노출합니다**(5점 만점 소수 1자리) — 상세는 `01_rubric.md` 7절.

**D28 — BYOK(체험 1회 + 본인 키)** 와 **D29 — 체험 세션 동의**는 6.5절이 원본입니다.
**D27 — 예약 게이트**는 D28 이후 **체험 세션만** 배급하도록 적용 범위가 좁아졌습니다.
