## 1. 한 줄 정의와 MVP 범위

> IT 직군 경력자가 이력서와 JD를 넣고 **심층 압박형 / 기술 검증형** 중 하나를 골라
> **음성으로 모의면접**을 치른 뒤, **답변 원문이 인용된 평가 리포트**를 받는다.

MVP에서 마지막까지 남는 셋: **이력서를 읽은 꼬리질문 / 원문 인용 평가 / 음성 대화.**

## 2. 네이밍 규칙 (전 팀 공통 — 경계 불일치의 유일한 예방책)

```
DB (Postgres)  : snake_case   예) session_id, created_at, main_question_budget
API 응답        : camelCase    예) sessionId, createdAt, mainQuestionBudget
프론트 타입      : camelCase (API 응답과 동일)
변환 시점        : API 라우트에서 단 한 번. 프론트에서도, DB 레이어에서도 변환하지 않는다.
```

- status enum 값(`in_progress` 등), 루브릭 축 식별자(`job_knowledge` 등), 라우트 경로는
  **camelCase로 바꾸지 않고 문자열 그대로** 오갑니다. 이들은 필드명이 아니라 값이기 때문입니다.
- 문서 서술은 한국어, 그 안의 식별자는 영어입니다. status 값이나 컬럼명을 한국어로 번역하면
  CHECK 제약과 API 계약이 깨집니다.

## 3. 사용자 여정

브리프 3절대로 사용자는 **특정 공고의 서류 합격 이후 D-7**에 들어옵니다. 상시 접속형 제품이 아닙니다.

| # | 단계 | 입력 | 출력 | 이탈 시 세션 상태 |
|---|---|---|---|---|
| 1 | 가입·로그인 | 이메일 | 세션 없음 | — |
| 2 | 세션 설정 | 직군, 페르소나, 모달리티, 이력서(파일 또는 텍스트), JD(파일 또는 텍스트) | 설정 완료된 세션 | `created` / `configuring` |
| 3 | 준비 | 마이크 권한 확인 | 컨텍스트 요약 + 오프닝 질문 | `ready` |
| 4 | 면접 | 음성 또는 텍스트 답변 | 꼬리질문 루프, 전사 로그 | `paused` |
| 5 | 종료 | 종료 조건 충족 또는 사용자 종료 | 대화 로그 확정, 평가 큐 등록 | `completed` |
| 6 | 평가(비동기) | 대화 로그 + 루브릭 | 축별 점수·인용·개선점 | `evaluating` |
| 7 | 리포트 열람 | — | 점수, 원문 인용, 개선점 | `evaluated` |
| 8 | 피드백·이의 제기 | 유용성 응답, 항목별 이의 | 지표 4·5 데이터 | `evaluated` |
| 9 | 재시도 | 같은 이력서로 새 세션 | 회차 간 비교 | 새 세션 `created` |

각 단계의 상태·전이·복구 경로는 `01_state_machine.md`가 원본입니다.

**핵심 이탈 방어 2곳**
- 5→7 사이(지표 2 리포트 도달률): 평가가 비동기라 사용자가 떠날 수 있습니다. 목록과 대시보드에
  "새 리포트" 배지를 두고, 리포트 대기 화면은 완료 시 자동 갱신합니다.
- 7→9 사이(지표 3 재시도율, 북극성): 리포트 하단에 **"같은 이력서로 다시 하기"** 버튼을 두어
  설정을 다시 채우지 않고 새 세션을 시작하게 합니다(직군·페르소나·문서 그대로 복제).

## 5. 전사 오류 정정 (브리프 9절 #3 결정)

**결정: 정정 기능을 넣되, 범위를 "직전 자기 발화"로 제한한다.**

- 면접 중, 사용자는 **자기 마지막 답변** 한 건만 인라인 편집할 수 있습니다. 다음 질문이 나온 뒤에는
  그 답변을 더 이상 고칠 수 없습니다(그 답변을 근거로 이미 꼬리질문이 만들어졌기 때문).
- 정정 시 STT 원문은 `turns.transcript_raw`에 보존하고, `transcript_text`가 수정본이 됩니다.
  이후 모든 질문 생성과 평가·인용은 `transcript_text`를 씁니다. `is_corrected = true`로 표시합니다.
- 면접관(AI) 발화는 편집 불가입니다.
- 리포트 화면에서는 편집 대신 **이의 제기**로 처리합니다(`reason_code = 'transcription_error'`).
  MVP에서 이의 제기는 재평가를 유발하지 않고 데이터만 수집합니다. `[later]`로 재평가 연결.

**근거.** 음성 원본을 저장하지 않으므로 전사가 평가 근거의 유일한 원천이고(브리프 7절),
무료 티어 STT는 정확도가 낮습니다(7절 함의 4). 정정 수단이 없으면 잘못된 인용이 리포트에 남아
핵심 가치 2번이 무너지고 이의 제기율(지표 5)만 올라갑니다. 반대로 전체 로그를 자유 편집하게 하면
사후 답변 미화가 가능해져 회차 간 비교(핵심 가치 3번)가 무의미해지고, 이미 생성된 꼬리질문과
로그가 어긋납니다. "직전 발화만"이 두 위험 사이의 최소 지점입니다.

## 6. 이력서·JD 텍스트 추출 (브리프 9절 #5 — 초안 결정)

**초안 결정: 서버(Next.js Route Handler, Node.js 런타임)에서 추출한다.** 최종 확정은 `vercel-platform-engineer`.

| 방안 | 판단 |
|---|---|
| 클라이언트 파싱 | 기각 — PDF 파서가 번들을 크게 키우고 브라우저·기기별 결과 편차가 생김. 결과 재현이 어려움 |
| **서버 파싱** | **채택** — 무료 티어 안에서 처리 가능(추가 과금 $0), 텍스트 정규화 규칙을 한 곳에서 관리, 실패를 서버 로그로 추적 |
| LLM에 파일 직접 투입 | 기각 — 무료 티어 토큰을 크게 소모하고 프로바이더 파일 API에 종속됨. 예산 제약 위반 |

- 흐름: 업로드 → Storage 저장 → 서버에서 텍스트 추출 → `documents.extracted_text` 저장 →
  `extraction_status`를 `succeeded` / `failed`로 기록.
- 추출 결과는 사용자에게 **보여주고 편집 가능하게** 합니다. 추출 품질이 질문 품질을 좌우하므로
  사용자가 확인 없이 넘어가면 안 됩니다.
- 텍스트 레이어가 없는 스캔 PDF는 MVP에서 `failed`로 처리하고 텍스트 직접 입력을 안내합니다. OCR은 `[later]`.
- 파일 크기 상한 10MB, 허용 확장자 `pdf` / `docx` / `txt` / `md`.

### 리포트 화면의 피드백 수집 UI (지표 4·5 — 필수)

1. **유용성 피드백** (지표 4): 리포트 하단 "이 피드백이 도움이 되었나요?" — 도움됨 / 도움 안 됨 + 선택 코멘트.
   세션당 1회 저장, 수정 가능. `report_feedback`에 기록.
2. **항목별 이의 제기** (지표 5): 각 축 점수 카드와 각 인용문 옆에 "이건 아닌 것 같아요".
   사유 코드를 고르게 합니다 — `transcription_error`(제 말과 다름) / `misinterpreted`(의도를 잘못 읽음) /
   `score_too_low`(점수가 부당함) / `other`. `score_disputes`에 기록.
   지표 5는 "축 점수 카드 노출 대비 클릭 비율"로 계산하므로 카드 노출 이벤트도 남깁니다.

## 8. 범위 밖 (하지 않을 것)

브리프 6절 Non-goals를 그대로 따릅니다: 화상·표정 분석, 공유·랭킹·커뮤니티, 결제·구독,

- 경험 탐색형 페르소나와 신입 타깃 흐름

- 알림 이메일 (리포트 완료 알림은 앱 내 배지로만)

무료 티어 기본 SMTP는 시간당 발송 한도가 낮아 외부 프로바이더가 필요해지고, 이는 "무료 티어 안에서
해결"이라는 예산 제약과 충돌합니다. 평가가 1~2분이면 사용자가 대기 화면에 머물 가능성이 높아 손실이
작습니다. 먼저 지표 2(리포트 도달률)의 베이스라인을 보고 다시 판단합니다.

**D4 — 이의 제기(지표 5)는 수집만 하고 재평가를 유발하지 않습니다.**
무료 티어 호출을 추가로 쓰지 않고 구현이 단순합니다. 다만 사용자가 "눌러도 아무 일 없음"으로 느낄 수
있으므로, 이의 제기 후 **접수되었다는 확인과 그 사유가 다음 개선에 쓰인다는 안내**를 UI에 반드시
노출해야 합니다. 이것이 없으면 지표 5 자체가 수집되지 않습니다.
