## 리더 결정의 근거

### D5 — `wrap_up`은 `turns`에만
`wrap_up`은 질문이 아니라 마무리 발화입니다. `questions`에 넣으면 지표 6(세션당 최초 질문 대비
후속 질문 수의 중앙값)의 분모가 세션마다 1씩 부풀어, 제품 정체성을 재는 유일한 지표가 왜곡됩니다.
`questions_kind_shape` CHECK도 그대로 유지됩니다.

### D6 — `documents`는 스냅샷 (잠정값 뒤집음)
보존이 무기한이고 삭제가 **실제 삭제**이므로, 참조만 두면 사용자가 이력서를 고치거나 지운 순간
과거 세션의 "무엇을 읽고 이 질문을 했는지"가 사라집니다. 핵심 가치 3번(회차 간 비교)은
**같은 이력서로 다시 봤을 때의 변화**를 보는 것이므로, 근거 문서가 흔들리면 비교 전제 자체가 무너집니다.
또 참조만 두면 문서 삭제 시 세션을 cascade로 지우거나(리포트 유실) FK를 NULL로 만들어야 하는데
둘 다 나쁩니다. 스냅샷은 이 선택을 없앱니다.

비용은 D3(원본 파일 보관)과 달리 **텍스트뿐**이라 세션당 수십 KB 수준이고, 무료 티어 DB 용량에서
차지하는 비중이 작습니다. 용량을 무겁게 만드는 쪽은 파일이지 텍스트가 아닙니다.

→ `interview_sessions`에 `resume_text_snapshot` / `jd_text_snapshot` 추가 필요.

### D7 — `paused` 7일 (잠정값 뒤집음)
결정적인 이유는 **레이트 리밋**입니다. 무료 티어는 분당뿐 아니라 **일당(RPD) 한도**가 걸리고,
`pause_reason = 'rate_limited'`로 멈춘 세션은 구조적으로 다음 날에야 재개할 수 있습니다.
24시간 시한은 이 경우 재개 창과 정확히 겹쳐, 예산 제약이 만든 중단을 사용자 이탈로 기록하게 됩니다.
완주율(지표 1)이 압박 강도가 아니라 무료 티어 한도를 재게 되는 셈입니다.

부수적으로 브리프 3절의 "D-7 집중 연습" 창과 7일이 정확히 겹칩니다. `paused` 행이 더 오래 쌓이지만
부분 인덱스가 있어 비용은 무시할 수준이고, 스케줄러는 일 1회 그대로 둡니다.

### D8 — confirm email 끔
무료 티어 기본 SMTP는 시간당 발송 한도가 낮아, 켜두면 예산 제약("무료 티어 안에서 해결")과 충돌하는
외부 SMTP 프로바이더가 필요해집니다. D2에서 이메일 발송 경로를 두지 않기로 한 것과도 일관됩니다.
MVP는 첫 사용자 20~30명 규모의 베이스라인 수집 기간이라 오타 가입 위험보다 외부 의존성 0이 낫습니다.

**남는 위험:** 잘못된 이메일로 가입하면 계정 복구 경로가 없습니다. 로그인 화면에 이메일 확인 문구를
두고, 사용자가 늘어 복구 요청이 실제로 발생하면 그때 켭니다.

### D9 — 삭제된 세션의 지표를 남기지 않음
"실제 삭제"는 브리프 7절의 확정 제약입니다. 해시로 익명화하더라도 사용자가 지운 세션의 흔적이
남는 것은 그 약속과 어긋납니다. 지표는 아직 베이스라인 수집 단계라 정확도보다 원칙이 우선하고,
삭제율이 높게 나오면 그때 다시 판단합니다.

### D10 — 코치 시도 횟수 컬럼 없음
컬럼 하나를 관측 목적으로 늘리기보다, 이미 있는 `session_events`로 코치 실패를 셀 수 있습니다.
필요해지면 ALTER 한 줄입니다. `attempt_count`가 평가자 시도만 센다는 사실은 문서에 명시합니다.

### D11 — Google 단독
`02_ai_architecture.md` 4.4절이 프로바이더 추상화를 이미 필수 구현 요구사항으로 두고 있으므로,
2중화는 나중에 환경변수 교체로 전환할 수 있습니다. 처음부터 2중화하면 두 모델의 프롬프트를
병행 튜닝해야 해서 12주 일정에 부담이고, 레이트 리밋 방어는 이미 4단 폴백 사다리가 담당합니다.

### D12 — `rubric_version`이 다르면 비교하지 않음
축 정의나 가중치가 바뀐 뒤의 점수는 이전 회차와 같은 척도가 아닙니다. 경고를 띄우고 보여주면
사용자는 숫자를 먼저 읽고 경고는 나중에 읽습니다. MVP에는 `rubric_version`이 하나뿐이라 실질
영향이 없고, 비용은 회차 비교 화면(`[later]`)에 분기 하나를 두는 것뿐입니다.

### D13 — 시드 원형 60개는 Phase 3에서 작성
LLM 생성만으로는 직군 특유의 깊이가 나오지 않고, 사람이 60개를 직접 쓰는 것은 12주 일정에
부담입니다. `ai-interview-architect`가 12.3절 형식대로 작성하고 `product-architect`가 직무 적합성을
리뷰하는 분담이 `02_ai_architecture.md` 12.1절의 "혼합" 결정과 일치합니다.

### D14 — 5초 예산의 t=0은 엔드포인트 확정 시점
`voice-pipeline-engineer`가 정당하게 제기한 문제입니다. "답변 종료"를 **사용자의 마지막 음절**로 읽으면
침묵 임계값 3초가 통째로 더해져 최대 7.5초가 되어 5초를 지킬 수 없고, 임계값을 1초로 낮추면
면접 중 생각하느라 멈춘 사용자의 말을 끊습니다. 둘 다 받아들일 수 없습니다.

**t=0을 VAD가 발화 종료를 판정한 시점(엔드포인트 확정)으로 정의합니다.**
근거는 브리프가 5초 제약을 둔 이유 자체에 있습니다 — "5초의 침묵은 사용자에게 오류로 보인다"는 것입니다.
그런데 침묵 대기 구간은 UI가 `listening`으로 명확히 표시하고 있으므로 오류로 보이지 않습니다.
오류로 보이는 것은 **`thinking` 구간**입니다. 따라서 5초 예산은 `thinking`에 적용하는 것이
브리프의 의도에 정확히 맞습니다. 예산을 느슨하게 만드는 재정의가 아니라, 재려던 것을 제대로 재는 것입니다.

함께 확정합니다.
- 침묵 임계값은 **종결 어미 적응형 1,800ms를 기본**으로 합니다(단정적 종결 어미 뒤에는 짧게, 그 외에는 길게).
- **"답변 완료" 버튼을 1급 경로로 제공**합니다. 사용자가 기다리기 싫으면 즉시 넘길 수 있어야 합니다.
- `listening` 구간이 길어질 때의 카운트다운 예고를 UI 요구사항으로 둡니다.

### D15 — 자동 barge-in은 MVP 기본 off
브라우저 내장 TTS에서 에코 취소의 실효를 확인하지 못한 상태로 자동 barge-in을 켜면,
면접관 자신의 목소리가 사용자 발화로 인식되어 **면접이 진행 자체가 불가능해질 수 있습니다.**
실패 모드가 "기능이 없다"가 아니라 "제품이 동작하지 않는다"이므로 켜고 시작하지 않습니다.
수동 "답변 시작" 버튼으로 끼어들기 요구는 충족합니다. Phase 3에서 V5(에코 유입량) 실측 후 재검토합니다.

### D16 — 브라우저 STT의 외부 전송은 안내 문구로 고지
Chrome 계열은 음성을 음성 인식 제조사 서버로 보낼 수 있습니다. 이것은 **브라우저의 동작이지
우리 서비스의 처리가 아니므로**, 우리가 동의를 받을 주체가 아닙니다. 다만 "음성을 저장하지 않는다"는
약속을 사용자가 "내 목소리는 어디에도 안 간다"로 읽을 수 있으므로, 오해를 방치하지 않고
**마이크 권한 요청 화면에 안내 문구를 노출**합니다. 별도 동의 체크박스는 두지 않습니다 —
거부해도 대안이 텍스트 모드뿐이라 실질적 선택지가 아니고, 텍스트 모드는 이미 1급 경로로 제공됩니다.

`docs/`의 개인정보 정책은 사람 소유 문서이므로 이 사실을 반영할지는 사용자 판단입니다.

### D17 — `<<<META>>>` 보류 버퍼의 스트림 종료 처리 (M8)
계약에 스트림이 보류 버퍼를 남긴 채 끝났을 때의 규칙이 없어, **마지막 글자 유실**과
**`<<<META` 조각의 발화 누출** 두 방향의 버그가 모두 가능했습니다. `02_ai_contracts.md` 3.2절에
M8 규칙을 추가했습니다: 보류분이 센티널의 진부분 문자열이면 완성될 가능성이 0이므로 발화로 flush 하고,
보류분을 버리는 경로는 두지 않습니다.

### D18 — 평가 시작은 서버가 한다
`01_state_machine.md`(서버 자동)와 `05_api_contract.md` #16(클라이언트 훅)이 갈렸습니다. **상태 머신이 맞습니다.**

결정적인 반례는 `paused` 7일 자동 종료(D7)입니다. 스케줄러가 답변 ≥ 1인 세션을 `completed`로 보낼 때
**클라이언트는 아예 존재하지 않습니다.** 클라이언트가 평가를 시작하는 구조라면 이 세션들은 영원히
평가되지 않고 `completed`에 갇힙니다. 사용자가 마지막 답변 직후 탭을 닫는 흔한 경우도 마찬가지입니다.

`completed`로 가는 **모든** 경로의 부작용으로 서버가 평가를 등록합니다.
`POST /api/sessions/[sessionId]/evaluate`는 없애지 않되 **`failed` 상태에서의 재시도 전용**으로
의미를 좁힙니다. `completed`나 `evaluating`에 호출하면 409를 반환합니다.

### D19 — `canceled`는 삭제가 아니라 종료 상태
`01_state_machine.md` 안에서 모순이 있었습니다. 2절은 `canceled`의 부작용을 전부 "실제 삭제"로 적었는데,
행이 지워지면 `status = 'canceled'`는 **어떤 행에도 존재할 수 없는 값**이 됩니다. CHECK 제약에만 있고
관측은 불가능한 유령 상태였고, 3절은 목록에 "취소됨"으로 보인다고 적어 정면으로 어긋났습니다.

**취소와 삭제를 분리합니다.**
- `canceled`는 행을 남기는 **종료 상태**입니다. 세션 목록의 기본 필터에서는 숨기고,
  "취소된 세션 보기" 토글로만 노출합니다.
- **삭제는 기존 `DELETE /api/sessions/[sessionId]` 경로로만** 일어나고, 되돌릴 수 없다는 확인을 거칩니다.

제품 관점에서도 이쪽이 옳습니다. 면접 도중 "이 세션 버리기"를 누른 사용자가 확인 절차 없이 대화 기록을
영구 파괴당할 이유가 없습니다. 파괴적 동작은 명시적 확인을 거친 삭제 경로 하나로 모읍니다.

**상태 목록 11개와 CHECK 제약은 그대로입니다** — 값의 의미만 정정되고 enum은 바뀌지 않습니다.

### D20 — 기존 피드백·이의 제기는 평가 응답에 실어 보낸다
`PUT .../feedback`과 `POST .../disputes`만 있고 조회 경로가 없어, 새로고침하면 D4가 요구한
"접수되었습니다" 확인이 사라지고 사용자가 같은 이의를 다시 제기해 **지표 5가 중복으로 오염**됩니다.

엔드포인트를 새로 늘리는 대신 **`GET .../evaluation` 응답에 사용자의 기존 피드백과 이의 목록을
포함**합니다. 리포트 화면은 이미 이 하나를 호출하므로 왕복이 늘지 않고, "리포트를 여는 것"과
"내가 이 리포트에 무엇을 남겼는지"는 화면상 분리될 이유가 없습니다.

### D21 — 문서 삭제 전 영향 건수
`DELETE` 응답에만 건수가 있어 **누르기 전에는 경고할 수 없었습니다.** 확인 다이얼로그가 영향 범위를
모른 채 뜨는 셈입니다. `GET /api/documents/[id]` 응답에 `linkedSessionCount`를 넣습니다.

D6(스냅샷)으로 문서를 지워도 과거 리포트는 온전하므로, 경고 문구는 "과거 리포트가 손상된다"가 아니라
**"이 문서를 쓴 세션 N개에서 출처 표시가 사라진다"** 가 되어야 합니다.

### D22 — 토스트는 `sonner`
`06_ui_plan.md`가 `sonner`와 Radix Toast 직접 조립 사이에서 미결로 남겨 두어, QA가 shadcn-only 제약을
판정할 수 없다고 보고했습니다.

**`sonner`를 씁니다.** shadcn/ui가 자체 Toast를 대체해 공식 채택한 컴포넌트이므로,
"다른 UI 라이브러리 도입 금지" 제약에 걸리는 외부 라이브러리가 아닙니다. `npx shadcn add sonner`로
들어오는 것은 shadcn 컴포넌트 그 자체입니다. Radix Toast를 직접 조립하는 쪽은 접근성 처리를
스스로 떠안게 되어 이득이 없습니다.

**이 예외는 `sonner` 하나에 한정됩니다.** 차트·드롭존·아이콘팩·애니메이션 라이브러리는 여전히 금지이며,
`06_ui_plan.md`가 직접 조립하기로 한 6개 컴포넌트 결정은 그대로 유지합니다.

### D23 — 비밀번호 재설정은 노출한다
`06_ui_plan.md`가 마지막 미결로 남긴 항목입니다. 이메일 발송 경로가 하나도 없는데 재설정 링크를
노출하면 눌러도 메일이 오지 않고, 감추면 사용자는 방법이 없다는 것조차 모릅니다.

**세 번째 답이 맞습니다 — 재설정 메일은 보냅니다.**

D2와 D8을 다시 읽으면 둘 다 재설정을 금지하지 않습니다. D2는 **리포트 완료 알림**을 보내지 않기로 한
것이고, D8은 **가입 확인**을 끈 것입니다. 둘 다 "발송량이 사용자 활동에 비례해 늘어나는" 경로여서
무료 SMTP 한도와 충돌했습니다. 비밀번호 재설정은 성격이 다릅니다 — **드물게, 사용자가 명시적으로
요청할 때만** 발송되므로 시간당 한도에 닿지 않습니다.

무엇보다 D8이 남긴 위험이 "잘못된 이메일로 가입하면 계정 복구 경로가 없다"였는데,
재설정마저 막으면 **올바른 이메일로 가입한 사용자까지 복구 경로를 잃습니다.** 그것은 받아들일 수
없는 대가입니다. 재설정은 계정 복구의 유일한 경로이므로 남깁니다.

`/login`에 "비밀번호를 잊으셨나요?"를 정상 노출합니다.

### D24 — Preview AI 키는 운영과 분리
분리하지 않으면 **PR 검증 몇 번이 그날 실제 사용자가 받을 수 있는 리포트 수를 깎습니다.**
무료 티어의 일당 한도(RPD)는 환경을 구분하지 않기 때문입니다. 개발 활동이 프로덕션 가용성을
직접 잠식하는 구조를 남길 이유가 없고, 무료 티어라 키를 하나 더 만드는 비용은 0입니다.
실측 전에 결정해도 뒤집힐 위험이 없는 쪽입니다.

### D25 — 하트비트 90초 규칙 폐기
`01_state_machine.md` 2절이 "90초 하트비트 끊김 → `paused(connection_lost)`"를 규정했지만,
무료 플랜에는 분 단위 크론이 없어 **90초를 판정할 수단이 존재하지 않습니다.** 관측할 수 없는 규칙을
계약에 남기면 구현 불가이거나, 더 나쁘게는 아무도 지키지 않는 거짓 문장이 됩니다.

계약 옵션 A를 채택합니다.
- 클라이언트가 이탈을 감지하면 `sendBeacon`으로 **즉시** `paused(connection_lost)`를 최선 노력 호출
- 감지하지 못한 경우(브라우저 강제 종료 등)는 **일 1회 워치독**과, 사용자가 다시 열었을 때의
  **지연 판정**으로 회수합니다. 평가 워치독(`05_api_contract.md` 6.2절)과 같은 방식입니다

옵션 B(`session_events`에 하트비트 행)는 지표 1·2의 원천 테이블을 분당 1행씩 오염시키므로 기각,
옵션 C(`last_heartbeat_at` 컬럼)는 스키마를 늘려도 판정 주체가 여전히 일 1회 크론이라 이득이 없어 기각.
`01_state_machine.md` 2절 104행의 "90초" 문구를 위 서술로 대체합니다.

### D26 — 문서 추출은 동기 라우트 유지
PDF 추출은 AI 호출이 아니라 **지연이 예측 가능**하고(1~8초), Node 런타임 `maxDuration 60` 안에 들어옵니다.
비동기로 바꾸면 상태·폴링·워커가 통째로 늘어나는데, 그 복잡도를 정당화할 만큼 오래 걸리는 작업이
아닙니다. 실패 경로는 이미 정의돼 있습니다(`extraction_status = 'failed'` → 텍스트 직접 입력).

**뒤집는 조건을 명시해 둡니다:** 실측에서 10MB PDF가 30초를 넘으면 평가와 같은 체이닝으로 옮깁니다.
업로드 단계의 파일 크기 제한이 이 조건의 1차 방어선입니다.

### D27 — $0 유지, 벽을 세션 시작 전으로 옮긴다

사용자가 **"비용은 문자 그대로 0원"** 을 확정했습니다. 따라서 프로바이더 선택은 그대로입니다 —
Claude API는 전 모델이 종량 과금이라(최저가 Haiku 4.5가 $1/$5 per MTok) 후보가 될 수 없고,
Google AI Studio 무료 티어를 씁니다. `02_ai_architecture.md` 4.2절의 모델 선택은 변경 없습니다.

**다만 무료 티어 한도를 방어하는 방식을 바꿉니다.**

지금까지의 설계는 순전히 **사후 대응**이었습니다 — 429를 받으면 그때 폴백 사다리를 내려가고,
마지막 단계에서 `paused` + `pause_reason = 'rate_limited'`로 면접을 중단시켰습니다.
이 구조에서는 **벽이 항상 면접 도중에 옵니다.** 26번째 호출에서 걸릴지 3번째에서 걸릴지 모르는 채로
시작하기 때문입니다. 사용자는 30분을 쏟은 뒤에 끊깁니다.

한 세션의 호출량이 **26회로 예측 가능**하다는 것이 열쇠입니다. 그러므로 시작 시점에 여력을 확인하고
예약할 수 있습니다.

- **세션을 시작하기 전에** 오늘 남은 여력을 확인하고 한 세션분을 예약한다.
- 여력이 없으면 **세션을 만들지 않고** "오늘은 여기까지"를 안내한다.
- 세션이 예약분을 다 쓰지 않고 끝나면(조기 종료·취소) 남은 예약을 **반납**한다.
- `pause_reason = 'rate_limited'`는 없애지 않되 **예외 경로로 강등**한다. 정상 경로에서는 발생하지 않아야
  하고, 발생하면 예약 모델이 틀렸다는 신호이므로 관측 대상이다.
- 폴백 사다리 1~3단계(TTS 텍스트화 → STT 텍스트 전환 → 백오프)는 유지한다. 분당 한도(RPM)의
  순간적 초과는 여전히 사후 대응이 맞다. 사전 예약이 다루는 것은 **일당 한도(RPD)** 다.

**이것은 사용자 등급이 아닙니다.** 사용자를 나누지 않고 전원이 같은 하루 여력을 나눠 씁니다.
브리프 6절의 "사용량 제한 없음, 인증된 사용자는 무제한"과 충돌하지 않습니다 — 개인별 상한이 아니라
서비스 전체의 가용성이고, 성격은 점검 중인 서버에 가깝습니다. 사용자에게 "무료 티어"나 "한도"라는
말을 노출하지 않습니다.

**왜 이 대가를 받아들이는가:** 30분 면접을 치르다 끊기는 것과 시작 전에 "지금은 안 됩니다"를 듣는 것은
사용자 입장에서 전혀 다른 일입니다. $0을 유지하는 비용은 어차피 누군가 치러야 하는데,
그것이 **진행 중인 면접**이 되어서는 안 됩니다.

**메커니즘은 각 소유자가 정합니다** — 예약 원장의 형태(새 테이블 vs 기존 데이터 파생),
반납 시점, 여력 조회 쿼리는 `02_ai_architecture.md`가 모델을 정의하고 `04`·`05`·`06`이 따릅니다.

### D28 — BYOK (체험 1회 + 본인 키)

사용자가 본인의 Gemini API 키를 연결해 **자기 토큰으로** 면접을 봅니다. D27의 예약 게이트가
공유 자원을 배급하는 방식이었다면, BYOK는 **자원 자체를 사용자별로 분리**합니다.

**형태: 체험 1회 + 이후 BYOK.**
- 첫 세션은 공용 키로 키 없이 돌린다. 사용자는 꼬리질문과 리포트를 먼저 경험한다.
- 그 다음부터는 본인 키를 연결한다. **리포트를 본 직후가 키를 요구하기 가장 좋은 순간**이다 —
  재시도율이 북극성 지표라는 것과 정확히 맞물린다.
- 공용 풀이 바닥나도 **BYOK 사용자는 영향받지 않는다.**

**D27의 예약 게이트는 버려지지 않고 역할이 좁아진다.** 이제 **체험 세션만** 배급한다.
`02_ai_architecture.md` 8.3절의 원장·예약·반납 모델은 그대로 쓰되 적용 범위가 체험으로 한정된다.

**이 구조의 진짜 이득은 막혔을 때 출구가 생긴다는 것이다.** 여력이 없을 때 할 수 있는 말이
"내일 오세요"에서 **"키를 연결하면 지금 바로 시작할 수 있어요"** 로 바뀐다. 같은 벽인데 다른 경험이다.

**받아들이는 대가:** 온보딩에 단계가 하나 늘어난다. 타깃이 면접 D-7의 급한 사용자라 이 마찰은
가볍지 않으므로, **순서로 방어한다** — 가치를 먼저 보여주고 그 다음에 요구한다.

**보안 요구(새로 생기는 책임):** 타인의 자격증명을 보관하게 된다.
- 저장 시 **암호화 필수**(Supabase Vault). RLS만으로 부족하다.
- **클라이언트로 절대 되돌려주지 않는다.** 마스킹된 끝 4자리만 노출한다.
- 계정 삭제 시 키도 실제 삭제된다(D 삭제 정책과 동일).
- 키는 서버에서만 복호화되며 `NEXT_PUBLIC_` 계열 어디에도 닿지 않는다.

### D29 — 체험 세션의 데이터 처리 동의

Google Gemini API 무료(Unpaid) 서비스 약관을 2026-09-10에 확인한 결과입니다.

> "Google uses the content you submit to the Services and any generated responses to
> **provide, improve, and develop Google products**"
> "**human reviewers may read, annotate, and process** your API input and output"
> "**Do not submit sensitive, confidential, or personal information to the Unpaid Services.**"

Replai가 보내는 것은 **이력서(실명·경력·회사명·프로젝트)와 면접 답변**입니다. 약관이 보내지 말라고
명시한 범주에 정확히 해당합니다. 유료 티어는 제품 개선에 쓰지 않는다고 구분되어 있고,
EU·영국·스위스는 무료 티어에도 유료 수준 보호가 적용되지만 **한국은 해당되지 않습니다.**

**이것은 BYOK 이전에 기존 설계에 이미 해당되던 문제입니다.**

**BYOK가 이를 실질적으로 개선합니다.** 사용자가 결제를 활성화한 본인 키를 연결하면 유료 티어
데이터 보호가 적용되고, 비용은 사용자가 부담하며 소유자는 $0을 유지합니다. 무료 키를 연결하더라도
**본인 계정에서 본인 데이터에 대해 본인이 동의한** 구조가 됩니다. 즉 BYOK는 한도 회피 수단이 아니라
**프라이버시 업그레이드 경로**이며, 키를 요구하는 명분도 여기서 나옵니다.

**남는 구간은 체험 1회입니다** — 우리 키로, 낯선 사람의 이력서를, 사람이 읽을 수 있는 무료 티어에
보냅니다. 해결은 숨기지 않는 것뿐입니다. 체험 시작 전에 **평범한 한국어로 명시하고 동의를 받습니다.**
"무료 티어"·"쿼터" 같은 내부 용어를 쓰지 않고 무슨 일이 일어나는지 그대로 적습니다.

> 체험 면접은 Google의 무료 AI 서비스로 진행됩니다. 입력하신 이력서와 답변을 Google이 서비스
> 개선에 사용할 수 있고, 검토자가 읽을 수 있습니다.
> 본인 API 키를 연결하면 이 과정을 거치지 않습니다.

동의를 거부하면 체험을 시작하지 않고 **키 연결로 안내**합니다. 동의 사실은 시각과 함께 기록합니다.

**`docs/` 반영 필요(사람 소유, 리더가 고치지 않음):** 브리프 6절이 "음성 원본 보관"을 개인정보
항목으로 다루면서, 정작 **텍스트가 외부로 나가 사람이 읽을 수 있다**는 사실은 다루지 않습니다.
음성보다 이쪽이 큽니다. 개인정보 정책에도 반영되어야 합니다.

출처: [Gemini API 약관](https://ai.google.dev/gemini-api/terms)

### D30 — 체험 예약은 사용자당 동시 1건

`vercel-platform-engineer`가 계약 작업 중 발견한 구멍입니다.

`trial_consumed_at`은 **첫 주질문에 답한 시점**에 기록되는데, 예약은 **`prepare` 시점**에 잡힙니다.
그 사이가 벌어져 있어서, 세션을 여러 개 만들고 `prepare`만 반복하면 **실제 체험은 0회인데
`pro` 3 × N개를 동시에 점유**할 수 있습니다. `pro` 버킷이 체험 정원을 결정하므로
**한 사용자가 그날 전체 체험 정원을 잠글 수 있습니다.** 악의가 없어도 브라우저 탭을 몇 개 열어두면
발생합니다.

**체험 사용자가 이미 `held` 상태의 예약을 가지고 있으면 `prepare`의 두 번째 예약을 거절합니다(409).**

근거는 단순합니다 — 체험은 1회인데 동시 예약이 1건을 넘을 이유가 없습니다. 기존 예약을 버리고
새 세션으로 가고 싶으면 이전 세션을 취소하면 되고, 취소는 이미 반납을 부작용으로 갖습니다.

강제 지점은 **DB 함수**입니다. `reserve_session_quota`가 같은 사용자의 `held` 예약 존재를 확인하고
있으면 예외를 던집니다. 라우트에만 두면 동시 요청에서 빠져나갑니다 —
BYOK 세션의 원장 행을 함수가 막는 것과 같은 이유입니다.

BYOK 세션에는 해당하지 않습니다. 예약 자체를 하지 않기 때문입니다.

### D31 — Vercel Hobby는 300초. 평가 체이닝을 단순화한다

**2026-09-10 측정 결과, 설계의 전제가 틀렸습니다.** Vercel Hobby 플랜의 함수 `maxDuration`은
**기본값 300초이자 최대값 300초**입니다(Pro는 최대 800초). 설계는 60초를 가정하고 평가자와 코치를
**별도 함수 호출로 체이닝**해 각 단계를 실행 상한 아래로 밀어 넣었습니다. 그 회피책의 이유가 사라졌습니다.

평가자 ≤50초 + 코치 ≤40초 + 재시도를 합쳐도 300초 안에 넉넉히 들어옵니다.

**단, 두 단계를 논리적으로 합치지는 않습니다.** 독립 재시도와 부분 성공(코치가 실패해도 점수·인용은
남는다)은 의도된 성질이고 `improvement`가 nullable인 이유이기도 합니다. 바꾸는 것은 **전송 계층뿐**입니다 —
두 단계를 **하나의 워커 호출 안에서 순차 실행**합니다.

없어지는 것: 내부 HTTP 홉 1개, `JOB_SECRET` 왕복 1회, "1단계는 성공했는데 2단계 호출이 유실되는"
실패 모드 1종. `evaluate` 라우트가 202를 즉시 반환하고 `waitUntil`로 워커를 띄우는 구조는 그대로입니다.

### D32 — Gemini는 `minLength`/`maxLength`를 강제하지 않는다

**2026-09-10 확인.** Gemini 구조화 출력이 지원하는 JSON Schema 키워드 목록에
**`minLength`·`maxLength`가 없습니다.** 지원되는 것은 `type`·`title`·`description`·`properties`·
`required`·`additionalProperties`·`enum`·`format`·`minimum`·`maximum`·`items`·`prefixItems`·
`minItems`·`maxItems`입니다.

**설계에 유리한 쪽으로 확인된 것들:**
- `enum` 지원 → 루브릭 축 5개 고정이 스키마에서 강제됩니다
- `additionalProperties: false` 지원 → **평가자 출력에 `weight`·`overall_score`·`summary` 자리가
  없다는 책임 경계가 스키마로 강제**됩니다. 이 설계의 핵심 장치가 살아 있습니다
- `minItems`/`maxItems` 지원 → 축 정확히 5개, 인용 1–3건이 강제됩니다
- `minimum`/`maximum` 지원 → 점수 1–5 정수가 강제됩니다
- `["integer","null"]` 방식의 nullable → 근거 부족 시 `score = null`이 그대로 동작합니다

**강제되지 않는 것은 인용 길이 하나뿐입니다.** 20–160자는 **서버 검증이 유일한 강제 수단**이며,
DB CHECK가 최종 방어선입니다. 설계가 이미 서버 이중 검사를 두고 있어 동작은 바뀌지 않지만,
계약이 "스키마가 막아준다"고 읽히면 안 되므로 **명시적으로 못박습니다.**

### D33 — `middleware.ts` → `proxy.ts`

스캐폴딩 중 Next.js 16.3.4가 빌드마다 경고를 냈습니다.

> `The "middleware" file convention is deprecated. Please use "proxy" instead.`

계약(`05_api_contract.md` 7.2절)이 `middleware.ts`를 명시하고 있었지만 **프레임워크를 따릅니다.**
파일명은 계약의 본질이 아니라 구현 세부이고, 빌드마다 뜨는 경고를 안고 가면 **경고를 무시하는 습관**이
생겨 정작 중요한 경고를 놓치게 됩니다. 지금 옮기는 비용은 파일명과 export 이름 두 줄입니다.

`src/proxy.ts`로 옮기고 export도 `proxy`로 바꿨습니다. 경고 0건, 빌드 정상.
계약 7.2절의 파일명 표기를 갱신합니다 — 동작과 보호 라우트 규칙은 그대로입니다.
