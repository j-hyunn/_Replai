## 리더 결정의 근거

### D5 — `wrap_up`은 `turns`에만
`wrap_up`은 질문이 아니라 마무리 발화입니다. `questions`에 넣으면 지표 6(세션당 최초 질문 대비
후속 질문 수의 중앙값)의 분모가 세션마다 1씩 부풀어, 제품 정체성을 재는 유일한 지표가 왜곡됩니다.
`questions_kind_shape` CHECK도 그대로 유지됩니다.

### D6 — `documents`는 스냅샷 (잠정값 뒤집음)
보존이 무기한이고 삭제가 **실제 삭제**이므로, 참조만 두면 사용자가 이력서를 고치거나 지운 순간
과거 세션의 "무엇을 읽고 이 질문을 했는지"가 사라집니다. 핵심 가치 3번(회차 간 비교)은
**같은 이력서로 다시 봤을 때의 변화**를 보는 것이므로, 근거 문서가 흔들리면 비교 전제 자체가 무너집니다.
또 참조만 두면 문서 삭제 시 세션을 cascade로 지우거나(리포트 유실) FK를 NULL로 만들어야 하는데
둘 다 나쁩니다. 스냅샷은 이 선택을 없앱니다.

비용은 D3(원본 파일 보관)과 달리 **텍스트뿐**이라 세션당 수십 KB 수준이고, 무료 티어 DB 용량에서
차지하는 비중이 작습니다. 용량을 무겁게 만드는 쪽은 파일이지 텍스트가 아닙니다.

→ `interview_sessions`에 `resume_text_snapshot` / `jd_text_snapshot` 추가 필요.

### D7 — `paused` 7일 (잠정값 뒤집음)
결정적인 이유는 **레이트 리밋**입니다. 무료 티어는 분당뿐 아니라 **일당(RPD) 한도**가 걸리고,
`pause_reason = 'rate_limited'`로 멈춘 세션은 구조적으로 다음 날에야 재개할 수 있습니다.
24시간 시한은 이 경우 재개 창과 정확히 겹쳐, 예산 제약이 만든 중단을 사용자 이탈로 기록하게 됩니다.
완주율(지표 1)이 압박 강도가 아니라 무료 티어 한도를 재게 되는 셈입니다.

부수적으로 브리프 3절의 "D-7 집중 연습" 창과 7일이 정확히 겹칩니다. `paused` 행이 더 오래 쌓이지만
부분 인덱스가 있어 비용은 무시할 수준이고, 스케줄러는 일 1회 그대로 둡니다.

### D8 — confirm email 끔
무료 티어 기본 SMTP는 시간당 발송 한도가 낮아, 켜두면 예산 제약("무료 티어 안에서 해결")과 충돌하는
외부 SMTP 프로바이더가 필요해집니다. D2에서 이메일 발송 경로를 두지 않기로 한 것과도 일관됩니다.
MVP는 첫 사용자 20~30명 규모의 베이스라인 수집 기간이라 오타 가입 위험보다 외부 의존성 0이 낫습니다.

**남는 위험:** 잘못된 이메일로 가입하면 계정 복구 경로가 없습니다. 로그인 화면에 이메일 확인 문구를
두고, 사용자가 늘어 복구 요청이 실제로 발생하면 그때 켭니다.

### D9 — 삭제된 세션의 지표를 남기지 않음
"실제 삭제"는 브리프 7절의 확정 제약입니다. 해시로 익명화하더라도 사용자가 지운 세션의 흔적이
남는 것은 그 약속과 어긋납니다. 지표는 아직 베이스라인 수집 단계라 정확도보다 원칙이 우선하고,
삭제율이 높게 나오면 그때 다시 판단합니다.

### D10 — 코치 시도 횟수 컬럼 없음
컬럼 하나를 관측 목적으로 늘리기보다, 이미 있는 `session_events`로 코치 실패를 셀 수 있습니다.
필요해지면 ALTER 한 줄입니다. `attempt_count`가 평가자 시도만 센다는 사실은 문서에 명시합니다.

### D11 — Google 단독
`02_ai_architecture.md` 4.4절이 프로바이더 추상화를 이미 필수 구현 요구사항으로 두고 있으므로,
2중화는 나중에 환경변수 교체로 전환할 수 있습니다. 처음부터 2중화하면 두 모델의 프롬프트를
병행 튜닝해야 해서 12주 일정에 부담이고, 레이트 리밋 방어는 이미 4단 폴백 사다리가 담당합니다.

### D12 — `rubric_version`이 다르면 비교하지 않음
축 정의나 가중치가 바뀐 뒤의 점수는 이전 회차와 같은 척도가 아닙니다. 경고를 띄우고 보여주면
사용자는 숫자를 먼저 읽고 경고는 나중에 읽습니다. MVP에는 `rubric_version`이 하나뿐이라 실질
영향이 없고, 비용은 회차 비교 화면(`[later]`)에 분기 하나를 두는 것뿐입니다.

### D13 — 시드 원형 60개는 Phase 3에서 작성
LLM 생성만으로는 직군 특유의 깊이가 나오지 않고, 사람이 60개를 직접 쓰는 것은 12주 일정에
부담입니다. `ai-interview-architect`가 12.3절 형식대로 작성하고 `product-architect`가 직무 적합성을
리뷰하는 분담이 `02_ai_architecture.md` 12.1절의 "혼합" 결정과 일치합니다.

### D14 — 5초 예산의 t=0은 엔드포인트 확정 시점
`voice-pipeline-engineer`가 정당하게 제기한 문제입니다. "답변 종료"를 **사용자의 마지막 음절**로 읽으면
침묵 임계값 3초가 통째로 더해져 최대 7.5초가 되어 5초를 지킬 수 없고, 임계값을 1초로 낮추면
면접 중 생각하느라 멈춘 사용자의 말을 끊습니다. 둘 다 받아들일 수 없습니다.

**t=0을 VAD가 발화 종료를 판정한 시점(엔드포인트 확정)으로 정의합니다.**
근거는 브리프가 5초 제약을 둔 이유 자체에 있습니다 — "5초의 침묵은 사용자에게 오류로 보인다"는 것입니다.
그런데 침묵 대기 구간은 UI가 `listening`으로 명확히 표시하고 있으므로 오류로 보이지 않습니다.
오류로 보이는 것은 **`thinking` 구간**입니다. 따라서 5초 예산은 `thinking`에 적용하는 것이
브리프의 의도에 정확히 맞습니다. 예산을 느슨하게 만드는 재정의가 아니라, 재려던 것을 제대로 재는 것입니다.

함께 확정합니다.
- 침묵 임계값은 **종결 어미 적응형 1,800ms를 기본**으로 합니다(단정적 종결 어미 뒤에는 짧게, 그 외에는 길게).
- **"답변 완료" 버튼을 1급 경로로 제공**합니다. 사용자가 기다리기 싫으면 즉시 넘길 수 있어야 합니다.
- `listening` 구간이 길어질 때의 카운트다운 예고를 UI 요구사항으로 둡니다.

### D15 — 자동 barge-in은 MVP 기본 off
브라우저 내장 TTS에서 에코 취소의 실효를 확인하지 못한 상태로 자동 barge-in을 켜면,
면접관 자신의 목소리가 사용자 발화로 인식되어 **면접이 진행 자체가 불가능해질 수 있습니다.**
실패 모드가 "기능이 없다"가 아니라 "제품이 동작하지 않는다"이므로 켜고 시작하지 않습니다.
수동 "답변 시작" 버튼으로 끼어들기 요구는 충족합니다. Phase 3에서 V5(에코 유입량) 실측 후 재검토합니다.

### D16 — 브라우저 STT의 외부 전송은 안내 문구로 고지
Chrome 계열은 음성을 음성 인식 제조사 서버로 보낼 수 있습니다. 이것은 **브라우저의 동작이지
우리 서비스의 처리가 아니므로**, 우리가 동의를 받을 주체가 아닙니다. 다만 "음성을 저장하지 않는다"는
약속을 사용자가 "내 목소리는 어디에도 안 간다"로 읽을 수 있으므로, 오해를 방치하지 않고
**마이크 권한 요청 화면에 안내 문구를 노출**합니다. 별도 동의 체크박스는 두지 않습니다 —
거부해도 대안이 텍스트 모드뿐이라 실질적 선택지가 아니고, 텍스트 모드는 이미 1급 경로로 제공됩니다.

`docs/`의 개인정보 정책은 사람 소유 문서이므로 이 사실을 반영할지는 사용자 판단입니다.

### D17 — `<<<META>>>` 보류 버퍼의 스트림 종료 처리 (M8)
계약에 스트림이 보류 버퍼를 남긴 채 끝났을 때의 규칙이 없어, **마지막 글자 유실**과
**`<<<META` 조각의 발화 누출** 두 방향의 버그가 모두 가능했습니다. `02_ai_contracts.md` 3.2절에
M8 규칙을 추가했습니다: 보류분이 센티널의 진부분 문자열이면 완성될 가능성이 0이므로 발화로 flush 하고,
보류분을 버리는 경로는 두지 않습니다.

### D18 — 평가 시작은 서버가 한다
`01_state_machine.md`(서버 자동)와 `05_api_contract.md` #16(클라이언트 훅)이 갈렸습니다. **상태 머신이 맞습니다.**

결정적인 반례는 `paused` 7일 자동 종료(D7)입니다. 스케줄러가 답변 ≥ 1인 세션을 `completed`로 보낼 때
**클라이언트는 아예 존재하지 않습니다.** 클라이언트가 평가를 시작하는 구조라면 이 세션들은 영원히
평가되지 않고 `completed`에 갇힙니다. 사용자가 마지막 답변 직후 탭을 닫는 흔한 경우도 마찬가지입니다.

`completed`로 가는 **모든** 경로의 부작용으로 서버가 평가를 등록합니다.
`POST /api/sessions/[sessionId]/evaluate`는 없애지 않되 **`failed` 상태에서의 재시도 전용**으로
의미를 좁힙니다. `completed`나 `evaluating`에 호출하면 409를 반환합니다.

### D19 — `canceled`는 삭제가 아니라 종료 상태
`01_state_machine.md` 안에서 모순이 있었습니다. 2절은 `canceled`의 부작용을 전부 "실제 삭제"로 적었는데,
행이 지워지면 `status = 'canceled'`는 **어떤 행에도 존재할 수 없는 값**이 됩니다. CHECK 제약에만 있고
관측은 불가능한 유령 상태였고, 3절은 목록에 "취소됨"으로 보인다고 적어 정면으로 어긋났습니다.

**취소와 삭제를 분리합니다.**
- `canceled`는 행을 남기는 **종료 상태**입니다. 세션 목록의 기본 필터에서는 숨기고,
  "취소된 세션 보기" 토글로만 노출합니다.
- **삭제는 기존 `DELETE /api/sessions/[sessionId]` 경로로만** 일어나고, 되돌릴 수 없다는 확인을 거칩니다.

제품 관점에서도 이쪽이 옳습니다. 면접 도중 "이 세션 버리기"를 누른 사용자가 확인 절차 없이 대화 기록을
영구 파괴당할 이유가 없습니다. 파괴적 동작은 명시적 확인을 거친 삭제 경로 하나로 모읍니다.

**상태 목록 11개와 CHECK 제약은 그대로입니다** — 값의 의미만 정정되고 enum은 바뀌지 않습니다.

### D20 — 기존 피드백·이의 제기는 평가 응답에 실어 보낸다
`PUT .../feedback`과 `POST .../disputes`만 있고 조회 경로가 없어, 새로고침하면 D4가 요구한
"접수되었습니다" 확인이 사라지고 사용자가 같은 이의를 다시 제기해 **지표 5가 중복으로 오염**됩니다.

엔드포인트를 새로 늘리는 대신 **`GET .../evaluation` 응답에 사용자의 기존 피드백과 이의 목록을
포함**합니다. 리포트 화면은 이미 이 하나를 호출하므로 왕복이 늘지 않고, "리포트를 여는 것"과
"내가 이 리포트에 무엇을 남겼는지"는 화면상 분리될 이유가 없습니다.

### D21 — 문서 삭제 전 영향 건수
`DELETE` 응답에만 건수가 있어 **누르기 전에는 경고할 수 없었습니다.** 확인 다이얼로그가 영향 범위를
모른 채 뜨는 셈입니다. `GET /api/documents/[id]` 응답에 `linkedSessionCount`를 넣습니다.

D6(스냅샷)으로 문서를 지워도 과거 리포트는 온전하므로, 경고 문구는 "과거 리포트가 손상된다"가 아니라
**"이 문서를 쓴 세션 N개에서 출처 표시가 사라진다"** 가 되어야 합니다.

### D22 — 토스트는 `sonner`
`06_ui_plan.md`가 `sonner`와 Radix Toast 직접 조립 사이에서 미결로 남겨 두어, QA가 shadcn-only 제약을
판정할 수 없다고 보고했습니다.

**`sonner`를 씁니다.** shadcn/ui가 자체 Toast를 대체해 공식 채택한 컴포넌트이므로,
"다른 UI 라이브러리 도입 금지" 제약에 걸리는 외부 라이브러리가 아닙니다. `npx shadcn add sonner`로
들어오는 것은 shadcn 컴포넌트 그 자체입니다. Radix Toast를 직접 조립하는 쪽은 접근성 처리를
스스로 떠안게 되어 이득이 없습니다.

**이 예외는 `sonner` 하나에 한정됩니다.** 차트·드롭존·아이콘팩·애니메이션 라이브러리는 여전히 금지이며,
`06_ui_plan.md`가 직접 조립하기로 한 6개 컴포넌트 결정은 그대로 유지합니다.

### D23 — 비밀번호 재설정은 노출한다
`06_ui_plan.md`가 마지막 미결로 남긴 항목입니다. 이메일 발송 경로가 하나도 없는데 재설정 링크를
노출하면 눌러도 메일이 오지 않고, 감추면 사용자는 방법이 없다는 것조차 모릅니다.

**세 번째 답이 맞습니다 — 재설정 메일은 보냅니다.**

D2와 D8을 다시 읽으면 둘 다 재설정을 금지하지 않습니다. D2는 **리포트 완료 알림**을 보내지 않기로 한
것이고, D8은 **가입 확인**을 끈 것입니다. 둘 다 "발송량이 사용자 활동에 비례해 늘어나는" 경로여서
무료 SMTP 한도와 충돌했습니다. 비밀번호 재설정은 성격이 다릅니다 — **드물게, 사용자가 명시적으로
요청할 때만** 발송되므로 시간당 한도에 닿지 않습니다.

무엇보다 D8이 남긴 위험이 "잘못된 이메일로 가입하면 계정 복구 경로가 없다"였는데,
재설정마저 막으면 **올바른 이메일로 가입한 사용자까지 복구 경로를 잃습니다.** 그것은 받아들일 수
없는 대가입니다. 재설정은 계정 복구의 유일한 경로이므로 남깁니다.

`/login`에 "비밀번호를 잊으셨나요?"를 정상 노출합니다.

### D24 — Preview AI 키는 운영과 분리
분리하지 않으면 **PR 검증 몇 번이 그날 실제 사용자가 받을 수 있는 리포트 수를 깎습니다.**
무료 티어의 일당 한도(RPD)는 환경을 구분하지 않기 때문입니다. 개발 활동이 프로덕션 가용성을
직접 잠식하는 구조를 남길 이유가 없고, 무료 티어라 키를 하나 더 만드는 비용은 0입니다.
실측 전에 결정해도 뒤집힐 위험이 없는 쪽입니다.

### D25 — 하트비트 90초 규칙 폐기
`01_state_machine.md` 2절이 "90초 하트비트 끊김 → `paused(connection_lost)`"를 규정했지만,
무료 플랜에는 분 단위 크론이 없어 **90초를 판정할 수단이 존재하지 않습니다.** 관측할 수 없는 규칙을
계약에 남기면 구현 불가이거나, 더 나쁘게는 아무도 지키지 않는 거짓 문장이 됩니다.

계약 옵션 A를 채택합니다.
- 클라이언트가 이탈을 감지하면 `sendBeacon`으로 **즉시** `paused(connection_lost)`를 최선 노력 호출
- 감지하지 못한 경우(브라우저 강제 종료 등)는 **일 1회 워치독**과, 사용자가 다시 열었을 때의
  **지연 판정**으로 회수합니다. 평가 워치독(`05_api_contract.md` 6.2절)과 같은 방식입니다

옵션 B(`session_events`에 하트비트 행)는 지표 1·2의 원천 테이블을 분당 1행씩 오염시키므로 기각,
옵션 C(`last_heartbeat_at` 컬럼)는 스키마를 늘려도 판정 주체가 여전히 일 1회 크론이라 이득이 없어 기각.
`01_state_machine.md` 2절 104행의 "90초" 문구를 위 서술로 대체합니다.

### D26 — 문서 추출은 동기 라우트 유지
PDF 추출은 AI 호출이 아니라 **지연이 예측 가능**하고(1~8초), Node 런타임 `maxDuration 60` 안에 들어옵니다.
비동기로 바꾸면 상태·폴링·워커가 통째로 늘어나는데, 그 복잡도를 정당화할 만큼 오래 걸리는 작업이
아닙니다. 실패 경로는 이미 정의돼 있습니다(`extraction_status = 'failed'` → 텍스트 직접 입력).

**뒤집는 조건을 명시해 둡니다:** 실측에서 10MB PDF가 30초를 넘으면 평가와 같은 체이닝으로 옮깁니다.
업로드 단계의 파일 크기 제한이 이 조건의 1차 방어선입니다.

### D27 — $0 유지, 벽을 세션 시작 전으로 옮긴다

사용자가 **"비용은 문자 그대로 0원"** 을 확정했습니다. 따라서 프로바이더 선택은 그대로입니다 —
Claude API는 전 모델이 종량 과금이라(최저가 Haiku 4.5가 $1/$5 per MTok) 후보가 될 수 없고,
Google AI Studio 무료 티어를 씁니다. `02_ai_architecture.md` 4.2절의 모델 선택은 변경 없습니다.

**다만 무료 티어 한도를 방어하는 방식을 바꿉니다.**

지금까지의 설계는 순전히 **사후 대응**이었습니다 — 429를 받으면 그때 폴백 사다리를 내려가고,
마지막 단계에서 `paused` + `pause_reason = 'rate_limited'`로 면접을 중단시켰습니다.
이 구조에서는 **벽이 항상 면접 도중에 옵니다.** 26번째 호출에서 걸릴지 3번째에서 걸릴지 모르는 채로
시작하기 때문입니다. 사용자는 30분을 쏟은 뒤에 끊깁니다.

한 세션의 호출량이 **26회로 예측 가능**하다는 것이 열쇠입니다. 그러므로 시작 시점에 여력을 확인하고
예약할 수 있습니다.

- **세션을 시작하기 전에** 오늘 남은 여력을 확인하고 한 세션분을 예약한다.
- 여력이 없으면 **세션을 만들지 않고** "오늘은 여기까지"를 안내한다.
- 세션이 예약분을 다 쓰지 않고 끝나면(조기 종료·취소) 남은 예약을 **반납**한다.
- `pause_reason = 'rate_limited'`는 없애지 않되 **예외 경로로 강등**한다. 정상 경로에서는 발생하지 않아야
  하고, 발생하면 예약 모델이 틀렸다는 신호이므로 관측 대상이다.
- 폴백 사다리 1~3단계(TTS 텍스트화 → STT 텍스트 전환 → 백오프)는 유지한다. 분당 한도(RPM)의
  순간적 초과는 여전히 사후 대응이 맞다. 사전 예약이 다루는 것은 **일당 한도(RPD)** 다.

**이것은 사용자 등급이 아닙니다.** 사용자를 나누지 않고 전원이 같은 하루 여력을 나눠 씁니다.
브리프 6절의 "사용량 제한 없음, 인증된 사용자는 무제한"과 충돌하지 않습니다 — 개인별 상한이 아니라
서비스 전체의 가용성이고, 성격은 점검 중인 서버에 가깝습니다. 사용자에게 "무료 티어"나 "한도"라는
말을 노출하지 않습니다.

**왜 이 대가를 받아들이는가:** 30분 면접을 치르다 끊기는 것과 시작 전에 "지금은 안 됩니다"를 듣는 것은
사용자 입장에서 전혀 다른 일입니다. $0을 유지하는 비용은 어차피 누군가 치러야 하는데,
그것이 **진행 중인 면접**이 되어서는 안 됩니다.

**메커니즘은 각 소유자가 정합니다** — 예약 원장의 형태(새 테이블 vs 기존 데이터 파생),
반납 시점, 여력 조회 쿼리는 `02_ai_architecture.md`가 모델을 정의하고 `04`·`05`·`06`이 따릅니다.

### D28 — BYOK (체험 1회 + 본인 키)

사용자가 본인의 Gemini API 키를 연결해 **자기 토큰으로** 면접을 봅니다. D27의 예약 게이트가
공유 자원을 배급하는 방식이었다면, BYOK는 **자원 자체를 사용자별로 분리**합니다.

**형태: 체험 1회 + 이후 BYOK.**
- 첫 세션은 공용 키로 키 없이 돌린다. 사용자는 꼬리질문과 리포트를 먼저 경험한다.
- 그 다음부터는 본인 키를 연결한다. **리포트를 본 직후가 키를 요구하기 가장 좋은 순간**이다 —
  재시도율이 북극성 지표라는 것과 정확히 맞물린다.
- 공용 풀이 바닥나도 **BYOK 사용자는 영향받지 않는다.**

**D27의 예약 게이트는 버려지지 않고 역할이 좁아진다.** 이제 **체험 세션만** 배급한다.
`02_ai_architecture.md` 8.3절의 원장·예약·반납 모델은 그대로 쓰되 적용 범위가 체험으로 한정된다.

**이 구조의 진짜 이득은 막혔을 때 출구가 생긴다는 것이다.** 여력이 없을 때 할 수 있는 말이
"내일 오세요"에서 **"키를 연결하면 지금 바로 시작할 수 있어요"** 로 바뀐다. 같은 벽인데 다른 경험이다.

**받아들이는 대가:** 온보딩에 단계가 하나 늘어난다. 타깃이 면접 D-7의 급한 사용자라 이 마찰은
가볍지 않으므로, **순서로 방어한다** — 가치를 먼저 보여주고 그 다음에 요구한다.

**보안 요구(새로 생기는 책임):** 타인의 자격증명을 보관하게 된다.
- 저장 시 **암호화 필수**(Supabase Vault). RLS만으로 부족하다.
- **클라이언트로 절대 되돌려주지 않는다.** 마스킹된 끝 4자리만 노출한다.
- 계정 삭제 시 키도 실제 삭제된다(D 삭제 정책과 동일).

### D30 — 체험 예약은 사용자당 동시 1건

`vercel-platform-engineer`가 계약 작업 중 발견한 구멍입니다.

`trial_consumed_at`은 **첫 주질문에 답한 시점**에 기록되는데, 예약은 **`prepare` 시점**에 잡힙니다.
그 사이가 벌어져 있어서, 세션을 여러 개 만들고 `prepare`만 반복하면 **실제 체험은 0회인데
`pro` 3 × N개를 동시에 점유**할 수 있습니다. `pro` 버킷이 체험 정원을 결정하므로
**한 사용자가 그날 전체 체험 정원을 잠글 수 있습니다.** 악의가 없어도 브라우저 탭을 몇 개 열어두면
발생합니다.

**체험 사용자가 이미 `held` 상태의 예약을 가지고 있으면 `prepare`의 두 번째 예약을 거절합니다(409).**

근거는 단순합니다 — 체험은 1회인데 동시 예약이 1건을 넘을 이유가 없습니다. 기존 예약을 버리고
새 세션으로 가고 싶으면 이전 세션을 취소하면 되고, 취소는 이미 반납을 부작용으로 갖습니다.

강제 지점은 **DB 함수**입니다. `reserve_session_quota`가 같은 사용자의 `held` 예약 존재를 확인하고
있으면 예외를 던집니다. 라우트에만 두면 동시 요청에서 빠져나갑니다 —
BYOK 세션의 원장 행을 함수가 막는 것과 같은 이유입니다.

BYOK 세션에는 해당하지 않습니다. 예약 자체를 하지 않기 때문입니다.

### D31 — Vercel Hobby는 300초. 평가 체이닝을 단순화한다

**2026-09-10 측정 결과, 설계의 전제가 틀렸습니다.** Vercel Hobby 플랜의 함수 `maxDuration`은
**기본값 300초이자 최대값 300초**입니다(Pro는 최대 800초). 설계는 60초를 가정하고 평가자와 코치를
**별도 함수 호출로 체이닝**해 각 단계를 실행 상한 아래로 밀어 넣었습니다. 그 회피책의 이유가 사라졌습니다.

평가자 ≤50초 + 코치 ≤40초 + 재시도를 합쳐도 300초 안에 넉넉히 들어옵니다.

**단, 두 단계를 논리적으로 합치지는 않습니다.** 독립 재시도와 부분 성공(코치가 실패해도 점수·인용은
남는다)은 의도된 성질이고 `improvement`가 nullable인 이유이기도 합니다. 바꾸는 것은 **전송 계층뿐**입니다 —
두 단계를 **하나의 워커 호출 안에서 순차 실행**합니다.

없어지는 것: 내부 HTTP 홉 1개, `JOB_SECRET` 왕복 1회, "1단계는 성공했는데 2단계 호출이 유실되는"
실패 모드 1종. `evaluate` 라우트가 202를 즉시 반환하고 `waitUntil`로 워커를 띄우는 구조는 그대로입니다.

### D32 — Gemini는 `minLength`/`maxLength`를 강제하지 않는다

**2026-09-10 확인.** Gemini 구조화 출력이 지원하는 JSON Schema 키워드 목록에
**`minLength`·`maxLength`가 없습니다.** 지원되는 것은 `type`·`title`·`description`·`properties`·
`required`·`additionalProperties`·`enum`·`format`·`minimum`·`maximum`·`items`·`prefixItems`·
`minItems`·`maxItems`입니다.

**설계에 유리한 쪽으로 확인된 것들:**
- `enum` 지원 → 루브릭 축 5개 고정이 스키마에서 강제됩니다
- `additionalProperties: false` 지원 → **평가자 출력에 `weight`·`overall_score`·`summary` 자리가
  없다는 책임 경계가 스키마로 강제**됩니다. 이 설계의 핵심 장치가 살아 있습니다
- `minItems`/`maxItems` 지원 → 축 정확히 5개, 인용 1–3건이 강제됩니다
- `minimum`/`maximum` 지원 → 점수 1–5 정수가 강제됩니다
- `["integer","null"]` 방식의 nullable → 근거 부족 시 `score = null`이 그대로 동작합니다

**강제되지 않는 것은 인용 길이 하나뿐입니다.** 20–160자는 **서버 검증이 유일한 강제 수단**이며,
DB CHECK가 최종 방어선입니다. 설계가 이미 서버 이중 검사를 두고 있어 동작은 바뀌지 않지만,
계약이 "스키마가 막아준다"고 읽히면 안 되므로 **명시적으로 못박습니다.**

**D11(Google 단독)은 재검토하지 않습니다.** 바뀌는 것은 모델 ID와 예약 산수뿐이고,
4.4절의 프로바이더 추상화가 정확히 이 상황을 위해 존재하므로 호출부는 건드리지 않습니다.

**결정 ① 5개 역할 전부 `gemini-3.1-flash-lite`.** 역할별로 모델을 나누지 않는 것은 취향이 아니라

요청량 0인 버킷은 예약 루프에서 건너뜁니다.

**결정 ② Pro 부재는 모델이 아니라 파이프라인으로 보상합니다 — 평가자 2패스.**
정직하게 적습니다: **손실을 보상하는 설계이지, 손실이 없다는 주장이 아닙니다.**
초안이 Pro를 고른 근거("인용 정확도와 채점 일관성이 제품 신뢰의 전부", 핵심 가치 2번)는

limit_calls   = floor(500 × 0.85) = 425      (안전 여유 15%)

**비-Lite `gemini-3.1-flash`는 존재하지 않습니다**(카탈로그 확인) — 이 ID를 쓰지 마십시오.

### D35 — Google OAuth 로그인과 "데모 체험" (로그인 없이 진짜 면접)

사용자가 두 가지를 확정했습니다. **① 데모는 진짜 AI를 호출한다**(타이핑 애니메이션이 아니라
실제 `interviewer` → `evaluator` 파이프라인). **② 데모는 로그인 없이 누구나 바로 입장한다.**

이 두 결정은 기존 설계의 세 지점과 정면으로 부딪힙니다 — 하루 12세션뿐인 체험 정원(D34 결정③),
`auth.uid()`를 전제로 한 RLS 고정 제약, 그리고 "체험 1회는 로그인한 사용자에게"라는 D28의 전제입니다.
아래는 그 세 지점을 각각 어떻게 푸는지이며, **D27·D28·D29·D30 어느 것도 뒤집지 않습니다.**

#### D35-1. 데모의 쿼터 — **별도 키 풀 위의 별도 버킷.** 체험 12세션은 한 톨도 건드리지 않는다

**결론: 제시된 (a)를 채택하되, "같은 원장의 새 버킷"에 한 가지를 더 붙입니다 —
그 버킷은 반드시 별도의 Gemini API 키 풀을 가리켜야 합니다.**

**왜 (b)를 기각하는가.** (b)는 같은 `trial_shared` 풀을 우선순위로 나누자는 안인데,
D34의 산수가 그 여지를 남겨두지 않았습니다.

```
flash_lite 유효 한도 = floor(500 × 0.85) = 425
체험 12세션          = 12 × 34            = 408
남는 여력            = 425 − 408          = 17   ← 데모 세션 1건도 채 안 된다(아래 17 참조)
```

**남는 것이 없으므로 "가장 낮은 우선순위"는 사실상 "항상 거절"입니다.** 우선순위 로직을 구현해 놓고
실제로는 늘 막히는 기능을 만드는 셈이고, 어쩌다 한 건 통과하면 그날의 체험 정원이 12에서 11로
줄어듭니다. **(b)는 안전 여유 15%를 잠식하는 방식으로만 동작합니다.** 그 여유는 프로바이더 측
내부 재시도와 `overflow` 계상을 흡수하려고 둔 것이라(8.3.1·8.3.7절) 데모에 빌려줄 수 없습니다.

**왜 "새 버킷"만으로는 부족한가 — 버킷은 원래 모델이 아니라 "독립된 RPD 카운터"다.**
`ai_quota_ledger`의 `model_bucket`을 모델 단위로 둔 근거는 "RPD가 모델마다 따로 걸린다"는 사실
하나였습니다(8.3.1절). 그런데 무료 티어의 RPD는 **모델별로, 그리고 프로젝트(키)별로** 걸립니다.
같은 키·같은 모델을 두 행으로 쪼개면 `limit_calls` 합이 실제 한도를 넘어 **원장이 거짓말을 시작합니다** —
원장이 "여력 있음"이라고 답한 상태에서 프로바이더가 429를 돌려주는, D27이 없애려던 바로 그 상황입니다.

따라서 버킷의 정의를 **"(키 풀 × 모델) 하나에 대응하는 독립 카운터"** 로 정확히 하고,
데모에는 **별도 AI Studio 프로젝트에서 발급한 두 번째 무료 키**를 붙입니다. 비용은 여전히 $0입니다.

| 항목 | 값 |
|---|---|
| 신규 버킷 값 | **`flash_lite_demo`** (`model_bucket` CHECK가 3종 → **4종**) |
| 버킷이 쓰는 키 | `GEMINI_API_KEY_DEMO` — **운영 공용 키와 다른 프로젝트의 키**. `NEXT_PUBLIC_` 금지 |
| 모델 | `gemini-3.1-flash-lite` (D34 — 전 역할 동일) |
| **데모 세션당 예약량** | **`AI_RESERVE_FLASH_LITE_PER_DEMO = 17`** |
| **하루 데모 정원** | **`AI_DEMO_DAILY_SESSIONS = 10`** |
| 원장 `limit_calls` | `10 × 17 = 170`. 애플리케이션이 계산해 `p_limits`로 주입(8.3.5절과 동일한 방식) |
| 체험 버킷 `flash_lite` | **변경 없음.** `limit_calls` 425, 하루 12세션 그대로 |

**17의 내역 — 데모 세션은 짧다.** 데모는 맛보기이므로 세션 파라미터를 낮춰 잡습니다
(`main_question_budget = 2`, `max_follow_up_depth = 2`, `max_turns = 6`, `max_duration_min = 12`.
전부 기존 CHECK 범위 안이라 **DDL 변경이 없습니다**).

| 몫 | 정상 | 재시도 여유 | 소계 |
|---|---|---|---|
| 면접관 턴 | 6 | 2 | 8 |
| 요약 | 1 | 0 | 1 |
| 플래너 | 1 | 1 | 2 |
| 평가자 패스 A + 패스 B | 2 | 2 | 4 |
| 코치 | 1 | 1 | 2 |
| | | | **17** |

`POST_INTERVIEW_HOLD`는 체험과 동일하게 **6**(평가 4 + 코치 2)입니다 — 면접이 끝나도 리포트 몫은
남겨야 한다는 8.3.4절 규칙이 그대로 적용됩니다. **코치를 빼서 15로 줄이지 않았습니다**:
데모의 목적은 리포트가 진짜라는 것을 보여주는 것이고, 개선점이 빠진 리포트는 그 주장을 약하게 만듭니다.

**D27의 원자적 예약 게이트(8.3.1절)와 어떻게 맞물리는가 — 함수는 한 줄도 새로 쓰지 않습니다.**

1. `reserve_session_quota(p_session_id, p_quota_date, p_request, p_limits)`의 **시그니처 불변**.
   데모 세션은 `p_request = {"pro":0,"flash":0,"flash_lite":0,"flash_lite_demo":17}`로 부릅니다.
   요청량 0인 버킷을 건너뛰는 D34의 `continue` 한 줄 덕분에 **데모 예약은 `flash_lite` 원장 행을
   읽지도, 만들지도, 잠그지도 않습니다.** 두 풀의 격리가 코드가 아니라 **데이터로** 보장됩니다.
2. **고정 버킷 처리 순서는 `pro → flash → flash_lite → flash_lite_demo`** 로 확장합니다.
   새 값을 **맨 끝에** 붙이는 것이 중요합니다 — 순서를 바꾸면 데드락 회피 근거(8.3.5절)가 깨집니다.
3. **재원 가드(D28)를 3분기로 넓힙니다.** 기존은 `funding_source <> 'trial_shared'`면 예외였습니다.
   이제는 **재원과 버킷의 짝을 강제**합니다.

   | `funding_source` | 허용 버킷 | 위반 시 |
   |---|---|---|
   | `trial_shared` | `flash_lite`만 | `quota_bucket_mismatch:trial_shared` |
   | `demo` | `flash_lite_demo`만 | `quota_bucket_mismatch:demo` |
   | `byok` | 없음(예약 자체를 하지 않음) | `quota_not_applicable:byok` (기존) |

   **짝을 DB 함수에서 강제하는 이유는 D30과 같습니다** — 라우트에만 두면 분기 하나를 빠뜨리는 순간
   데모가 체험 정원을 갉아먹고, 그 증상은 "체험 정원이 왜인지 부족하다"로만 보여 원인을 찾을 수 없습니다.
4. **동시 예약 가드(D30)는 그대로 적용됩니다.** 데모 방문자도 `auth.users` 행을 가진 진짜 사용자이므로
   (D35-2), 같은 사용자의 `held` 예약 1건 제한이 **코드 변경 없이** 데모에도 걸립니다.
   탭 3개를 열어도 데모 예약은 1건입니다.
5. 반납·소비·만료 스윕·`before delete` 트리거는 **버킷 이름만 다를 뿐 전부 그대로**입니다.

**전제 조건 하나를 명시합니다 — `GEMINI_API_KEY_DEMO`가 없으면 데모는 켜지지 않습니다.**
`NEXT_PUBLIC_DEMO_ENABLED`는 그 키의 존재를 전제로 운영자가 켜는 공개 플래그이며(키가 아니라 불리언이므로
`NEXT_PUBLIC_` 접두사가 허용됩니다), 꺼져 있으면 `/login`에 데모 버튼이 렌더되지 않고
`/demo`·`POST /api/demo/sessions`는 404를 돌려줍니다. **두 번째 키 없이 데모를 켜면
$0과 결정③을 동시에 지킬 수 없다**는 것이 위 산수의 결론이므로, 이것은 편의 기능이 아니라 **잠금장치**입니다.

**남는 `[확인 필요]` — D34와 같은 성격의 실측 항목 하나.**
무료 티어 RPD가 **프로젝트별인지 계정별인지**는 계정 설정에 따라 다를 수 있고, 2차 출처로 단정하지 않습니다.
`GEMINI_API_KEY_DEMO`를 발급한 뒤 **AI Studio 레이트 리밋 대시보드에서 두 키의 한도가 서로 독립인지
확인하는 것**을 데모 배포의 완료 조건에 넣습니다(D34가 정원 12를 실측으로 확정한 것과 같은 절차).
독립이 아니라면 데모는 켜지 않습니다 — 그 경우 결정③을 지킬 방법이 없기 때문입니다.
**추정으로 켜지 않습니다.**

#### D35-2. 데모 방문자의 식별과 남용 방어 — **Supabase 익명 인증을 채택한다**

**채택합니다.** "로그인 없음"은 사용자 경험의 서술이지 아키텍처의 서술이 아닙니다.
익명 로그인은 `auth.users`에 `is_anonymous = true`인 **진짜 행**을 만들고 `auth.uid()`를 발급하므로,
기존 RLS 정책(`(select auth.uid()) = user_id`)이 **한 줄도 바뀌지 않은 채** 데모에 그대로 적용됩니다.
고정 제약("사용자 데이터 테이블 전부 RLS")이 지켜지는 유일한 현실적 경로입니다.

**기각한 대안 2종.**
- *서명된 데모 토큰 + `service_role` 라우트로만 접근* — RLS를 끄는 것이 아니라 **우회하는** 설계이고,
  라우트 하나만 가드를 빠뜨려도 타인의 데모 세션이 열립니다. 고정 제약의 정신에 반합니다.
- *데모 전용 공유 계정 하나에 모든 방문자의 세션을 몰아넣기* — 방문자 A가 방문자 B의 면접 전문을
  읽을 수 있습니다. RLS는 켜져 있는데 아무것도 막지 못하는, 가장 나쁜 형태입니다.

**계정 구분은 `profiles`에 저장합니다.** `auth.users.is_anonymous`를 매번 조인해 읽는 대신
가입 트리거(`handle_new_user`)가 값을 복사합니다 — `interview_sessions`·게이트·프록시가 전부
`public` 스키마만 읽으면 되게 하기 위함입니다.

| `profiles` 신규 컬럼 | 정의 |
|---|---|
| `account_type` | `text not null default 'registered'`, `check (account_type in ('registered','demo'))`. 트리거가 `new.is_anonymous`에서 채움 |
| `demo_consumed_at` | `timestamptz` null. 데모 1회 소진 시각. `trial_consumed_at`과 **별개 컬럼**(의미가 다르고, 한 계정이 둘 다 갖는 일은 없다) |

`handle_new_user`는 `split_part(new.email, '@', 1)`로 `display_name`을 만드는데 익명 사용자는
**email이 NULL**입니다. `coalesce(split_part(new.email,'@',1), '데모 방문자')`로 고칩니다 —
고치지 않아도 NULL이 허용되지만, 화면에 빈 이름이 나오는 것보다 낫습니다.

**정리 정책 — 즉시 삭제가 아니라 TTL 24시간.**

즉시 삭제를 기각한 이유는 단순합니다. **평가는 비동기이고 리포트가 데모의 결론입니다.**
면접이 끝나는 순간 계정을 지우면 사용자는 자기가 방금 받은 점수를 못 봅니다 — 데모가 증명하려던
것을 정확히 그 시점에 없애는 셈입니다. 탭을 닫았다가 10분 뒤 돌아오는 경우도 흔합니다.

```
삭제 기준: auth.users.is_anonymous = true AND created_at < now() - interval '24 hours'
실행 주체: 크론 C1 GET /api/cron/daily 의 스윕 6종째 (기존 5종에 추가)
연쇄:      auth.users 삭제
             → profiles (on delete cascade)
               → interview_sessions → questions / turns / evaluations /
                 evaluation_scores / evaluation_citations / report_feedback / score_disputes
               → trial_consents (user_id cascade)
               → ai_quota_reservations (before delete 트리거가 원장에 여력 반납 — 3.14.2절)
             → session_events
```

- **Storage 객체는 생기지 않습니다.** 데모는 파일 업로드를 제공하지 않고 시드 문서만 씁니다(D35-3).
  따라서 `storage_cleanup_queue`에 들어갈 것이 없고, 삭제 경로가 DB 연쇄 하나로 끝납니다.
  이것은 부수 효과가 아니라 **데모가 업로드를 제공하지 않는 이유 중 하나**입니다.
- 24시간은 "리포트를 보고 돌아올 만한 시간"의 상한이자, 기존 보존 정책(무기한)의 **예외**입니다.
  예외를 두는 근거는 이 데이터의 소유자가 **되찾을 수 없는 계정**이라는 것입니다 — 익명 계정은
  복구 수단이 없으므로 무기한 보관해도 누구에게도 돌아가지 않고, 사람이 읽을 수 있는 무료 티어로
  이미 나간 답변만 DB에 쌓입니다. **지우는 쪽이 개인정보 결정과 일관됩니다.**
- 데모 리포트 화면과 `/demo` 입장 화면에 **"24시간 뒤 자동으로 삭제됩니다"** 를 명시합니다.
  숨기지 않는 것이 D29에서 택한 방식이고 여기서도 같습니다.

**같은 브라우저의 재입장 — 쿠키가 살아 있으면 같은 익명 사용자로 재사용됩니다.**
이것을 막지 않고 **이용합니다.** 재입장이 같은 계정으로 돌아오면 자기 리포트를 다시 볼 수 있고,
동시에 횟수 제한을 걸 자리가 생깁니다.

- **익명 사용자 1인당 데모는 24시간에 1회입니다.** `profiles.demo_consumed_at`이 NULL이 아니면
  `POST /api/demo/sessions`가 **409 `demo_already_consumed`** 를 돌려주고, 응답에 기존 세션 id를 실어
  UI가 "받은 리포트 다시 보기"로 보냅니다(D30의 `trial_reservation_exists`와 같은 형태).
- 채우는 시점은 `trial_consumed_at`과 **동일한 규칙**입니다 — 데모 세션에서 **첫 주질문에 답한 턴이
  저장되는 순간**, 같은 트랜잭션에서 `... where id = ... and demo_consumed_at is null`.
  입장만 하고 나간 사람에게 1회를 소모시키지 않습니다.

**쿠키를 지우고 익명 사용자를 계속 새로 만드는 경로 — 최소 장치 3종.**

| 장치 | 내용 | 성격 |
|---|---|---|
| **① 데모 버킷 자체가 상한** | 하루 10세션(`limit_calls = 170`). 익명 계정을 무한히 만들어도 **최대 10세션이 한도이고, 체험 12세션은 어떤 경우에도 줄지 않습니다** | **구조적 상한 — 이것이 본질적인 방어입니다** |
| ② 신규 익명 계정의 쿨다운 | `profiles.created_at`이 **10분 이내**이면서 이미 데모 세션 행을 가진 계정의 두 번째 요청을 409로 거절. `reserve_session_quota`의 D30 가드가 `held` 예약 1건으로 이미 대부분을 막으므로, 이것은 "예약을 반납시키고 새로 잡는" 패턴에 대한 보강 | 서버 라우트 |
| ③ 익명 로그인 자체의 레이트 리밋 | Supabase Auth의 익명 로그인 IP 레이트 리밋(+ 필요 시 CAPTCHA)을 켭니다. **대시보드 설정이므로 이 작업 범위 밖**이며, 운영자가 외부에서 설정하는 것을 전제로 합니다 | 프로바이더 설정 |

②를 "정교하게" 만들지 않는 이유를 적어 둡니다. 로그인 없는 페이지에서 사람과 봇을 확실히 가르는
방법은 없고, 시도할수록 진짜 방문자가 걸립니다. **우리가 실제로 지켜야 하는 것은 체험 정원 12세션이고,
그것은 ①이 데이터 구조로 이미 보장합니다.** 데모 10세션이 봇에게 소진되면 그날 데모가 닫히는 것뿐이며,
그 손실은 우리가 감수하기로 한 크기입니다.

**익명 사용자가 닿을 수 있는 범위를 좁힙니다.** `src/proxy.ts`(D33)가 `account_type = 'demo'`
(= `is_anonymous`) 세션을 **`/demo`, `/sessions/[id]/ready|interview|report|transcript`,
그리고 그에 대응하는 API로만** 통과시키고 나머지는 `/login`으로 302합니다.
특히 **`POST /api/sessions`(#3)와 `/settings/api-key` 계열은 익명 사용자에게 403**입니다 —
막지 않으면 익명 사용자가 `trial_shared` 세션을 만들어 체험 정원을 먹습니다.
**이 가드는 프록시와 DB 함수 양쪽에 둡니다**(D35-1의 재원↔버킷 짝 강제).

**익명 계정을 실계정으로 승격(link identity)하지 않습니다 — `[later]`.**
기술적으로는 가능하지만 데모 세션이 실사용자 지표로 딸려 들어오고(D35-3), `account_type`·
`demo_consumed_at`·`trial_consumed_at`의 전이 규칙을 새로 정의해야 합니다.
**가입하면 새 계정이고 체험 1회는 그대로 주어집니다.** 데모에서 본 리포트는 24시간 뒤 사라집니다 —
이것이 가입의 이유가 되므로 깔대기 관점에서도 손해가 아닙니다.

#### D35-3. 데모 데이터 — 시드 문서, 리포트, 지표 격리

**시드 이력서·JD는 직군 5종 × (이력서 1 + JD 1) = 10건입니다.**
직군은 브리프 3절이 정한 5개(`pm` `pd` `security` `ai` `engineer`)이고, 데모 방문자가 하는 선택은
**직군 하나뿐**입니다. 페르소나는 **`deep_pressure` 고정** — 제품의 차별점이 꼬리질문이고
심층 압박형이 그것을 가장 선명하게 보여줍니다. 모달리티만 음성/텍스트 중 고를 수 있습니다.
**선택지를 늘리지 않는 것이 요점입니다.** 데모는 설정 화면이 아니라 "한 번 눌러 면접에 들어가는" 화면입니다.

**소유는 전용 서비스 계정이 아니라 `documents`의 바깥입니다 — 신규 테이블 `demo_documents`.**

| 후보 | 판정 |
|---|---|
| 전용 서비스 계정이 소유한 `documents` 10행 | **기각.** `auth.users`에 사람 아닌 계정을 만들어야 하고(마이그레이션으로 만들기 어렵고 삭제 정책·RLS의 예외가 됨), `documents`의 모든 RLS 정책에 "단, 이 UUID는 예외" 분기가 생깁니다 |
| 데모 세션마다 `documents` 행 복제 | **기각.** 같은 텍스트가 방문자 수만큼 복사되고, TTL 삭제 경로가 하나 늘어납니다 |
| **신규 테이블 `demo_documents`** | **채택.** 이것은 사용자 데이터가 아니라 **우리가 작성한 픽스처**입니다. `user_id`가 없고, 마이그레이션으로 시드하며, RLS는 켜되 `select` 정책을 `authenticated`에 **전면 허용**합니다(익명 사용자도 `authenticated` 역할입니다). `insert/update/delete` 정책은 두지 않습니다 — 쓰기는 마이그레이션과 `service_role`뿐 |

```
demo_documents
  id           uuid PK
  job_role     text not null check (job_role in ('pm','pd','security','ai','engineer'))
  doc_type     text not null check (doc_type in ('resume','job_description'))
  title        text not null check (char_length(title) between 1 and 120)
  body_text    text not null check (char_length(body_text) between 1 and 200000)
  seed_version text not null           -- 문안을 고치면 올린다
  created_at   timestamptz not null default now()
  unique (job_role, doc_type)
```

**RLS를 어떻게 통과시키는가 — 통과시킬 일이 없습니다.**
데모 세션 생성 시 서버가 `demo_documents.body_text`를 읽어
`interview_sessions.resume_text_snapshot` / `jd_text_snapshot`에 **복사해 넣습니다.**
이것은 예외 처리가 아니라 **D6(문서는 스냅샷) 설계를 그대로 쓰는 것**입니다.
`resume_document_id` / `jd_document_id`는 **NULL**로 둡니다(둘 다 nullable).
그 결과 면접관·플래너·평가자는 **자기가 데모를 돌고 있다는 사실을 알 필요가 없습니다** —
스냅샷만 읽기 때문입니다. 프롬프트도 계약도 바뀌지 않습니다.

> **`configuring → ready` 가드에 분기가 하나 생깁니다.** 기존 가드는 "이력서/JD 문서가 있고
> `extraction_status = 'succeeded'`"였는데, 데모 세션에는 `documents` 행이 없습니다.
> `funding_source = 'demo'`이면 **스냅샷 2개가 채워져 있는지**로 판정합니다(`01_state_machine.md` 2절).

**리포트는 끝까지 보여줍니다. 배지를 답니다.**
평가까지 다 돌리기로 한 것이 사용자 결정(①)의 핵심이므로 리포트를 감추면 결정을 무효화하는 셈입니다.
다만 화면에는 **`Badge` "데모"** 와 한 줄 안내를 **상시** 답니다 —
면접 화면 헤더, 리포트 헤더, 전문 화면 헤더 3곳입니다.

> 이 면접은 미리 준비된 이력서로 진행한 데모 체험입니다. 기록은 24시간 뒤 자동으로 삭제됩니다.
> 내 이력서로 면접을 보려면 계정을 만들어 주세요.

**DB에는 실제 행으로 남깁니다. `funding_source = 'demo'`가 격리 장치입니다.**
데모를 별도 테이블로 빼지 않는 이유는 그렇게 하면 면접 루프·평가 워커·상태 머신이 **두 벌**이 되기 때문입니다.
"진짜 파이프라인을 돈다"는 결정이 곧 "같은 테이블을 쓴다"를 뜻합니다.

- `interview_sessions.funding_source` CHECK가 **`in ('trial_shared','byok','demo')`** 로 넓어집니다.
- **지표 1~6은 전부 `funding_source <> 'demo'`를 조건에 넣습니다.** 데모는 이력서가 남의 것이고
  세션 길이가 짧아(주질문 2개) 완주율·꼬리질문 깊이·재시도율을 **전부 왜곡합니다.**
  특히 지표 3(재시도율, 북극성)은 익명 계정이 7일 뒤 존재하지도 않으므로 구조적으로 0이 됩니다.
- **데모는 데모대로 셉니다** — 데모 세션 완주율과 `/demo → 가입` 전환은 `session_events`와
  `funding_source = 'demo'` 필터로 따로 봅니다. 섞지 않는 것이지 버리는 것이 아닙니다.
- `qa-inspector`에게: **집계 쿼리에서 이 필터가 빠진 곳을 찾는 것**을 상시 점검 항목으로 넘깁니다.

**데모에도 D29 동의가 필요합니다 — 문구만 다릅니다.**
이력서는 우리 것이지만 **방문자의 답변은 방문자의 것**이고, 그 답변이 사람이 읽을 수 있는
무료 티어로 나갑니다. D29가 요구한 것은 "무슨 일이 일어나는지 평범한 한국어로 알리고 동의받기"이므로
대상이 로그인 사용자냐 아니냐로 면제되지 않습니다.

- `consent_version = 'demo-1.0.0'` 으로 `trial_consents`에 **같은 형태로** 기록합니다
  (`user_id` = 익명 프로필 id, `session_id` = 데모 세션). 테이블·해시 규칙 변경 없음.
- 문구에서 **이력서 문장을 뺍니다**(우리 것이므로):
  > 데모 면접은 Google의 무료 AI 서비스로 진행됩니다. 답변하신 내용을 Google이 서비스 개선에
  > 사용할 수 있고, 검토자가 읽을 수 있습니다. 이 기록은 24시간 뒤 자동으로 삭제됩니다.
- 체험(D29)은 준비 직전 **다이얼로그**였지만, 데모는 **`/demo` 입장 화면의 체크박스**입니다.
  데모의 화면이 하나뿐이라 다이얼로그를 띄우면 한 화면에서 모달이 두 번 뜹니다.
  동의하지 않으면 시작 버튼이 `disabled`이고, **키 연결로 안내하지 않습니다** — 익명 사용자는
  키를 연결할 수 없습니다(D35-2 프록시 규칙). 대신 `/login`으로 안내합니다.

#### D35-4. Google OAuth

**Supabase Auth의 Google Provider를 그대로 씁니다. 자격 증명(Google Cloud OAuth 클라이언트,
Supabase 대시보드의 Provider 설정)은 이 작업 범위 밖이며, 외부에서 설정됨을 전제로 합니다.**
코드·문서에는 클라이언트 ID/시크릿이 등장하지 않습니다.

- **소셜 로그인은 `01_product_spec.md` 4.1절에서 `[later]`였습니다. `[MVP]`로 올립니다.**
  근거는 D8입니다 — 확인 메일을 끈 탓에 오타 주소로 가입하면 계정을 영영 못 찾는 위험을
  "감수한다"고 적어 두었는데, **Google 로그인은 그 위험 자체를 없앱니다**(주소를 사용자가 타이핑하지 않음).
  D8을 되돌리지 않고 위험만 줄이는 경로입니다. D23(비밀번호 재설정)도 그대로 둡니다.
- **콜백 라우트: `src/app/auth/callback/route.ts` → `GET /auth/callback`.**
  PKCE 코드를 `exchangeCodeForSession`으로 교환하고, `?next=`로 복귀합니다.
  `next` 검증 규칙은 **기존 `?next=` 규칙과 동일**합니다(`/`로 시작하고 `//`·`/\`가 아닌 내부 경로만.
  아니면 조용히 무시하고 기본값). 실패 시 `/login?error=oauth_failed`.
  - **라우트 그룹 `(auth)` 안에 두지 않습니다.** `(auth)`는 페이지용 그룹이고 이것은 라우트 핸들러입니다.
  - Google 콘솔의 리디렉션 URI는 Supabase가 제공하는 주소이며(외부 설정), 앱이 등록하는 것은
    Supabase의 `redirectTo`뿐입니다.
- **로그인 성공 후 랜딩:** `next`가 있으면 그 경로, 없으면 **`/dashboard`** — 기존 이메일 로그인과 동일합니다.
  경로를 두 벌로 만들지 않습니다.
- **`/login` 화면의 버튼 배치는 위계가 분명해야 합니다.**
  ① 맨 위 **[Google로 계속하기]**(`Button` 기본, 전체 너비) → `Separator` → ② 기존 이메일 탭
  (로그인/회원가입, D8 문구·D23 재설정 링크 유지) → ③ 카드 **바깥** 맨 아래에
  **[로그인 없이 데모 체험하기]**(`Button variant="ghost"`) + 한 줄 설명.
  - ③을 ①과 나란히 두지 않는 이유: 두 버튼이 같은 무게로 보이면 **가입하려던 사용자가 데모로 샙니다.**
    데모의 목적은 가입 전 확신을 주는 것이지 가입을 대체하는 것이 아닙니다.
  - `NEXT_PUBLIC_DEMO_ENABLED`가 꺼져 있으면 ③은 렌더되지 않습니다(D35-1).

#### 이 결정이 뒤집히는 조건

- **두 키의 무료 티어 한도가 독립이 아닌 것으로 실측되면** — 데모를 켜지 않습니다(D35-1).
- **데모 10세션이 매일 봇에게 소진되고 가입 전환이 0에 수렴하면** — 데모를 끕니다.
  `NEXT_PUBLIC_DEMO_ENABLED` 하나로 꺼지도록 설계한 이유입니다.
- **데모 전환율이 높아 정원을 늘리고 싶어지면** — 늘리는 것은 `AI_DEMO_DAILY_SESSIONS` 하나이고,
  **`flash_lite` 버킷은 그때도 건드리지 않습니다.**
